# 如何写好一个提示词：读完三大厂官方指南后的实操笔记

![如何写好一个提示词手绘全览](/images/how-to-write-prompts/prompt-guide.webp)

前两年网上到处都是“神级提示词”合集，像“请你深吸一口气”“做好了给你 200 美元小费”“你现在是拥有 30 年经验的世界顶级专家”。这些句子我以前也抄过不少，用顺手了就存进快捷短语里，每次提问前习惯性粘一段。

老实说，放到现在的新模型上，这套东西基本不管用了。我经常写了一整页要求，末尾还追着加了五六条“不要太长”“不要说废话”“要有深度”，结果模型写出来的东西还是端着架子，该漏的重点照样漏。

前几天索性不看二手文章了，直接去翻了三家模型厂商最新的官方文档：

- [Anthropic 官方 Prompt Engineering 指南](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)
- [OpenAI 官方 Prompt Engineering 指南](https://platform.openai.com/docs/guides/prompt-engineering)
- [Google Gemini 官方 Prompting Strategies 指南](https://ai.google.dev/gemini-api/docs/prompting-strategies)

三份文档看下来，挺意外的。里面没有藏着什么秘籍，全是很实在的用法。而且把三家放一块儿对照，就能发现哪些东西大家都认，哪些地方其实是各家模型脾气不一样。

---

## 一、三家文档看下来，哪些地方一致，哪些地方不一样

三家虽然互相竞争，但在几个核心问题上口径出奇地一致：

- **别跟模型兜圈子，把话说明白。** 平时我们找外包或者带新人干活，如果只丢一句“帮我做个好看点的页面”，对方交上来的大概率没法看。用大模型也是一样，背景、给谁看、做到什么程度算完，你心里有数，就得直接写出来。
- **把要求和原材料分开。** Anthropic 爱用 XML 标签（`<instructions>`、`<context>`、`<input>`），OpenAI 和 Gemini 常用 Markdown 标题或者分割线。写法随你挑，关键是别把你的规则和大段待处理的原文混在一起，不然模型看着看着就容易串台。
- **写代码调接口时，别靠嘴硬逼 JSON 格式。** 以前写后端代码，提示词最后总要加一句“只返回合法 JSON，前后绝对不要加任何文字”。现在 OpenAI 和 Gemini 的接口都原生支持 Structured Outputs，直接传 Pydantic 或 Zod 定义的 Schema 过去就行，省心多了。
- **别指望一次写对，得多测。** Anthropic 文档一上来就泼了盆冷水：动手调提示词之前，先想好怎么算成功、拿什么样例测。OpenAI 也反复强调，上线代码要锁死模型版本号，攒一套测试集（Evals）跑回归，别靠自己随手试一次觉得还行就上线。

比起共同点，三家文档里不一样的地方反而更值得看，不然拿一套写法到处套，很容易踩坑：

| 维度 | Anthropic（Claude） | OpenAI（GPT / 推理系列） | Google（Gemini） |
| :--- | :--- | :--- | :--- |
| **排版习惯** | 特别吃成对的 XML 标签，多层嵌套也能看明白 | 看重 `developer` / `system` 和 `user` 的权限分层 | 直接给了推荐顺序：角色 → 核心规则（最重要的放最前）→ 示例 → 输出格式 → 原始数据放最后 |
| **要不要写“一步步思考”** | 复杂问题里，让它先在 `<thinking>` 里推演再给结论挺管用 | **分模型看**：普通模型可以细化步骤；自带思考链的推理模型，再写“请一步步思考”反而多余，有时还会变差 | 遇到既要深度推理、又要严格 JSON 输出的任务，容易互相打架，最好拆成两步跑 |
| **怎么给例子（Few-Shot）** | 建议用 `<example>` 给 3 到 5 个不同情况的样例 | 用推理模型时，先什么例子都不给（Zero-Shot）直接试；非要给例子，例子必须跟上面的规则严丝合缝，不能打架 | 例子之间格式要完全统一，标点、缩进别乱变，跟任务无关的例子别硬塞 |

我自己读下来的体感是：OpenAI 的文档最偏工程接口视角，Anthropic 最像在教你怎么跟模型好好说话，Gemini 则把顺序和 Schema 讲得很细。但不管看哪家，趋势都很清楚：==模型越来越聪明之后，你不用再教它“怎么动脑子”，但你得把“你要什么、边界在哪”说准。==

## 二、先戒掉三个容易帮倒忙的习惯

对照着文档复盘了一下我以前写的提示词，有三个毛病以前老犯。

### 1. 开头先吹一段空洞头衔

“你是拥有 20 年经验的顶级架构师 / 文案大师”，这句话写完除了自己看着爽，其实说了跟没说一样。模型并不知道你心里的“顶级”长什么样。

不如直接交代视角和读者。比如改成：“你帮后端开发写接口文档。看文档的人赶时间，只想立刻知道这个接口干嘛用、参数有哪些坑、怎么在本地跑通，别写套话。”字数差不多，模型一下就知道按什么路子写了。

### 2. 一顺溜全写“不要……”

以前看到模型写得不对劲，我就往提示词后面补禁令：“不要用列表、不要太长、不要有翻译腔、不要总结”。

写完一堆“不要”，模型其实还是不知道你要它写成什么样。Anthropic 文档里举了个很直白的对比：与其写“不要用 Markdown 列表”，不如直接写“请用连贯的自然段来写”。直接告诉它怎么做，比在地上插满红牌管用。

### 3. 什么问题都硬往提示词里塞

Anthropic 专门单独写了一节讲“什么时候该调提示词”。很多时候效果不好，真不是提示词没写好。模型不知道你们公司最新的内部文档，你该接检索（RAG）；一个任务步骤太长，你该拆成两次调用；觉得太慢或者太贵，换个轻量模型比删改两百字提示词立竿见影。

## 三、我现在写提示词的五个习惯

落到平时写代码、整理资料和写文章里，如果遇到稍微复杂点的任务，我现在基本按这五个步骤来。

### 1. 先定清楚做到什么样算过关

动笔前先在脑子里过三件事：这东西给谁看？做到哪两三点我拿来就能直接用？我最怕它犯什么错（比如瞎编接口字段、漏掉边界条件、语气太浮夸）？

很多时候觉得模型笨，其实是我们自己对结果长什么样都没想明白，指望它替我们猜。

### 2. 用标签把规则和原材料隔开

稍微长一点的任务，我习惯按“先指令、后数据”的顺序写，用 XML 标签划清楚边界：

```xml
<role>
你当前的视角和要干的活
</role>

<context>
背景、给谁看、这份东西打算用在哪
</context>

<rules>
1. 最要紧的硬要求放第一条
2. 尽量直接说“怎么做”，少写一排“不要做”
3. 原文里没提到的信息直接写“待确认”，别自己编
</rules>

<output_format>
交代清楚结构、字数和语气
</output_format>

<input>
大段待处理的文本、代码或记录放最下面
</input>
```

这么写不光是给模型看的，我自己填这五个框的时候，经常顺手就能发现刚才漏了一个前提，或者有两条要求本来就互相打架。

### 3. 给关键要求补半句“为什么”

这是我看 Anthropic 文档时觉得最值的一招。

平时给模型提要求，我们习惯只丢一条死规矩，比如“文案控制在 30 字以内，别用专业术语”。模型会照着数数字，但分寸往往拿捏不准。

如果你顺手补半句原因：“文案控制在 30 字以内，别用专业术语，因为这句话要放在小程序首页的弹窗里，用户扫一眼只有两秒钟，看不明白就会直接点关闭。”

多这么半句，模型立刻就懂了你在什么场景下用这段话。它不光会控制字数，还会顺手把最重要的利益点放到前半句，把拗口的词换成大白话。==把原因交代给模型，比多写五条细则都省事。==

### 4. 少堆形容词，直接甩两个例子

提示词里写“专业、自然、接地气、通俗但不肤浅”，这种词给真人看也得愣半天。

与其琢磨形容词，不如直接翻两段你自己写过的、或者平时收藏的满意样例，放进 `<example>` 里让模型照着学。只要注意两点就行：几个例子的格式别前后乱变；例子本身别违反你上面定好的规则（比如上面写着不超过 100 字，下面例子却贴了 300 字）。

### 5. 复杂活儿拆成两步干

如果一件事既要模型“动脑子分析”，又要它“严格按某种格式排版或抽数据”，塞在同一轮里经常两边都做不好。

我现在的做法很干脆：第一步只让它放开手脚做分析、列问题；我看完觉得内容没毛病，第二步再把这份内容喂给它，专门让它改语气、缩字数或者转成固定格式。每一步只干一件事，哪一步歪了也能一眼看出来。

## 四、拿一个日常场景改一遍试试

平时开完产品评审会，把几千字的语音转文字丢给 AI 整理纪要，是最容易翻车的场景之一。

### 大多数人随手发的版本

> 帮我把下面这段会议记录总结一下，专业一点，条理清晰，不要太长，别漏掉重点。
>
> （后面直接粘 3000 字转写稿）

这么发出去，模型八成会给你整出“会议背景、核心议题、总结展望”三段式，把大家闲聊的话写成“各方就体验优化交换了意见”，而研发最关心的“哪个功能这期砍了”“接口字段周几定死”全被埋在字堆里。

### 改写后的版本

```xml
<role>
你是技术项目经理，负责把口语化的评审讨论整理成研发能直接照着干的执行纪要。
</role>

<context>
这份纪要会直接发到研发和测试群，作为本周排期和开发的对齐依据。大家赶进度没空看流水账，只关心拍板了什么、谁负责、什么时候交、哪些需求明确不做。
</context>

<rules>
1. 只记达成一致的结论和行动项；被否掉的提议或没聊出结果的讨论，放到“待确认”里，别把闲聊当结论。
2. 每条行动项写清负责人和截止时间；原文没提就写“待确认”，不要猜。
3. 直接写谁在什么时候做什么，别用“进行了深入交流”“达成广泛共识”这类套话。
</rules>

<output_format>
按下面四个二级标题输出，全文不超过 600 字：
## 一、已拍板结论（最多 5 条）
## 二、明确不做或延期的需求
## 三、行动项（格式：事项 | 负责人 | 截止时间）
## 四、待确认事项
</output_format>

<example>
<input>
小王说支付弹窗要不要加个倒计时，老李说这期工期太紧来不及，下期再说吧，大家说行。然后前端小红问订单状态字段是不是周五前定死，后端阿强说没问题周四下午给文档。
</input>
<output>
## 一、已拍板结论
- 订单状态字段定义由后端在周四下午前出文档冻结。

## 二、明确不做或延期的需求
- 支付弹窗增加倒计时：本期工期紧张，延期至下期迭代。

## 三、行动项
- 输出订单状态字段接口文档 | 阿强 | 本周四下午

## 四、待确认事项
- 暂无
</output>
</example>

<transcript>
{{在此粘贴原始会议语音转写稿}}
</transcript>
```

改完之后，同样那份 3000 字转写稿喂进去，效果稳定得多。因为我们把纪要发给谁看交代清楚了，把编造负责人这种最烦人的毛病提前堵死了，还专门留了一栏记“明确不做的需求”，省得开发理解错了白写代码；底下那段几十个字的样例，直接把干脆利落的口吻定下来了。

## 五、平时聊天和上线代码，别用同一套劲儿

当然，平时随便查个资料、写段小脚本，没必要每次都摆出一套 XML 五件套，那样反而把自己累着。我现在分两种情况用：

| 场景 | 怎么用 | 我常用的小技巧 |
| :--- | :--- | :--- |
| **日常聊天和探索** | 先简短说，多聊两轮 | 两三句话把目标和对象说清就行。碰到稍微复杂点的事，我喜欢在末尾补一句：“动笔前，先问我 3 到 5 个你觉得我还没说清楚的问题。”让模型反过来问我，比我自己闷头写半天要求省事多了。 |
| **写进代码的生产提示词** | 写严密，靠测试集迭代 | 把 `developer` / `system` 和 `user` 权限分开，用 XML 或 Markdown 分区，格式交给原生 JSON Schema；锁死模型版本，挑 10 到 20 条真实脏数据和边界用例做成回归测试，以后每次改提示词都跑一遍。 |

日常对话其实是在拿模型试水。等某个高频活儿聊顺了、坑也踩明白了，再把那套要求沉淀成固定模板写进工作流里。

## 结尾

Paul Graham 在[《超越聪明》](/translations/smart/)里写过，很多想法在动笔写之前其实是糊的，写着写着才理清楚。写提示词也差不多。==一条提示词改来改去总不满意，多半是因为我们自己对“到底想要什么”还没想透。==

下次觉得 AI 笨、听不懂人话的时候，先别急着去搜新模板。停下来想想：如果我现在把刚才那段话发给身边的同事，他能一次把活干对吗？如果连同事都得追着问我三遍，那真怪不到模型头上。
