# 如何写好一个提示词：读完三大厂官方指南后的实操笔记

![如何写好一个提示词手绘全览](/images/how-to-write-prompts/prompt-guide.webp)

过去两年，网上流传过不少“神级提示词”技巧。比如开头先写“请你深吸一口气”，或者“做好了给你 200 美元小费”，再配上一段“你是拥有 30 年经验的世界顶级专家”。

这些写法我大多试过。在早期模型上，偶尔确实能拉高一点输出质量；但换到今天的新一代模型，继续套用这类模板，效果往往很一般。有时候我写了一整页要求，后面还补了好几条“不要胡说”“不要太长”“要有深度”，结果模型给出来的还是空话连篇，重点依然没抓住。

后来我决定停下来，不再看二手总结，直接去读了三家模型厂商最新的官方文档：

- [Anthropic 官方 Prompt Engineering 指南](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)
- [OpenAI 官方 Prompt Engineering 指南](https://platform.openai.com/docs/guides/prompt-engineering)
- [Google Gemini 官方 Prompting Strategies 指南](https://ai.google.dev/gemini-api/docs/prompting-strategies)

三份文档摆在一起看，很多平时模模糊糊的体感突然对上了。它们没有藏着什么神秘技巧，讲的都是很朴素的工程常识。把三家的共同点和差异理清之后，我对“该怎么写提示词”有了更明确的判断。

---

## 一、三家官方文档里，哪些是共识，哪些是分歧

### 四个共同点

第一，把需求讲清楚，比任何技巧都管用。==三家文档都在开头强调同一件事：写提示词更像在给一位能力很强、但刚入职第一天的新同事交代工作。== 他懂通用知识，但不了解你的业务背景、读者是谁、以及你心里的及格线。如果你自己说得含糊，他只能按最稳妥、最平庸的方式去猜。

**第二，指令和原始材料必须分开。** Anthropic 推荐用 XML 标签（如 `<instructions>`、`<context>`、`<input>`），OpenAI 和 Gemini 推荐用 Markdown 标题或分隔符。形式不同，目的都一样：别把规则、背景信息和待处理的文本混在同一段里，防止模型漏看规则，或者被原始材料里的句子带偏。

**第三，工程场景下，尽量别靠提示词硬逼 JSON 格式。** 以前写代码调用接口，提示词末尾总要加一句“只返回合法 JSON，不要加任何解释文字”。现在 OpenAI 和 Gemini 都提供了原生的 Structured Outputs，可以直接把 JSON Schema（比如 Pydantic 或 Zod 定义）传给接口，在解码层保证格式合法。提示词本身只需要关注内容质量。

**第四，好提示词不是一次写出来的，是测出来的。** Anthropic 在总览页开头就写了三个前提：先定义什么算成功、再准备测试办法、最后才动手改初稿。OpenAI 也明确建议在生产环境锁定具体模型版本，并建立评测集（Evals）。只试跑一次看着顺眼，放到真实业务数据里大概率会翻车。

### 三个值得留意的差异

同样是写提示词，不同模型家族的习惯并不完全一样。拿同一套写法去套所有模型，有时反而会出问题：

| 维度 | Anthropic（Claude） | OpenAI（GPT / 推理系列） | Google（Gemini） |
| :--- | :--- | :--- | :--- |
| **结构偏好** | 对成对的 XML 标签解析很稳，适合多层嵌套 | 强调 `developer` / `system` 与 `user` 的角色权限分层 | 给出了明确的**顺序建议**：角色 → 核心规则（最重要的放最前）→ 示例 → 输出格式 → 原始数据放最后 |
| **思维链（CoT）** | 复杂任务里适合用 `<thinking>` 让模型先推演再输出 | **按模型区分**：普通模型可以细化步骤；自带内部思考链的推理模型，再写“请一步步思考”往往多余，甚至会拉低效果 | 深度推理与严格 JSON 约束同时存在时容易互相掣肘，建议拆成“先推理、再提取格式”两步 |
| **示例（Few-Shot）** | 常用 `<example>` 给 3 到 5 个不同场景的样本定调 | 面对推理模型建议先 **Zero-Shot** 直接跑；如果加示例，示例必须与规则完全一致，避免逻辑冲突 | 特别强调示例之间的格式保持一致（缩进、换行、标签不要变），无关示例会稀释注意力 |

这里面有一个很重要的变化：**模型能力越强，越不需要你替它规定“怎么思考”，但越需要你把“目标、边界和背景”说准。**

## 二、三个该戒掉的旧习惯

对照三家文档回头看自己以前的提示词，有三个习惯不仅没用，还经常帮倒忙。

### 1. 给模型戴空洞的大帽子

像“你是拥有 20 年经验的顶级文案大师”这类开头，几乎没有提供有效信息。“顶级”没有具体标准，模型并不知道你想要克制、幽默还是学术风格。

更有用的做法是交代**视角、读者和关注点**。比如改成：“你是负责给后端开发写文档的技术编辑。读者只关心这套方案解决什么问题、有哪些限制、怎么在本地跑起来，不需要营销措辞。”字数差不多，指向性清晰很多。

### 2. 堆满“不要……严禁……”的否定句

以前我看到输出不合心意，习惯一条条往上加禁令：“不要用列表、不要太长、不要像机器翻译、不要用总结句”。

问题是，只说“不要做什么”，模型依然不知道你希望它怎么做。Anthropic 的文档里举过一个很直接的例子：与其写“不要使用 Markdown 列表”，不如直接写“请用连贯的自然段落来写”。正面指令给出的是明确做法，比一排否定词好使。

### 3. 什么问题都想靠改提示词解决

Anthropic 专门有一节写《什么时候该做提示词工程》。不是所有问题都适合靠提示词硬解：模型缺私有业务知识，应该接检索（RAG）；单次任务步骤太多顾此失彼，应该拆成多步调用；觉得响应慢或者成本高，换一个更轻量的模型通常比删改提示词有效得多。

## 三、我现在怎么写提示词：五个具体步骤

把三家文档的建议落到日常工作里，我现在写一条较复杂的提示词，基本按这五步来。

### 1. 先明确“做到什么样算合格”

动笔前先想清楚三件事：
- 这份结果是给谁看的？
- 满足哪两三条要求，我拿到手几乎不用改？
- 这件事里，我最不能接受的错误是什么？（比如编造不存在的字段、漏掉边界条件、语气太夸张）

很多时候我们觉得模型不聪明，其实是我们自己还没把标准想清楚。

### 2. 用清晰区块隔开“规则”和“材料”

复杂任务我习惯按“先指令、后数据”的顺序写，用 XML 标签把不同部分隔开：

```xml
<role>
你当前的视角与职责
</role>

<context>
任务背景、目标读者、这份产出的实际用途
</context>

<rules>
1. 最关键的硬约束放在第一条
2. 尽量用正面描述说明“怎么做”
3. 原始材料里没提到的信息，直接标注“待确认”，不要自行补充
</rules>

<output_format>
明确结构、篇幅与语气
</output_format>

<input>
待处理的原始文本、代码或记录放最后
</input>
```

这套骨架的好处不只是方便模型解析，它也能帮你自己做一次自查。填完这五个区块时，经常能顺手发现漏掉的前提，或者提前揪出互相冲突的要求。

### 3. 给关键规则补一句“为什么”

这是 Anthropic 文档里对我启发最大的一点。

如果你只写“不要使用省略号和特殊符号”，模型遇到破折号、星号或者生僻英文缩写时，可能不知道该怎么处理。但如果你多补半句理由：“不要使用省略号和特殊符号，因为这段稿子会直接交给语音合成工具朗读”，模型就能理解背后的真实场景，顺带把不适合念出来的长句和表格也处理妥当。

==交代动机之后，一条死板的规则就会变成模型能自己举一反三的判断依据。==

### 4. 用两段示例替代一堆形容词

在提示词里写“专业、自然、有网感、通俗但不肤浅”，模型很难拿捏分寸。与其琢磨形容词，不如直接找两三个你真正满意的成品，放进 `<example>` 里给它照着学。

需要注意的是：几个示例之间的格式要保持一致；另外，示例里的内容必须严格遵守你上面写的规则。如果规则写着“不超过 100 字”，示例却贴了 300 字，模型就会无所适从。

### 5. 复杂任务拆成两步跑

如果一个任务同时需要“深度分析”和“严格排版 / 提取结构化数据”，塞进同一轮对话往往两边都做不好。

更稳妥的做法是拆开：第一步只管让模型把问题想透、把漏洞找全；确认内容没问题之后，第二步再把结果喂进去，专门负责精简字数、调整语气或转成固定格式。每一步只做一件事，排查问题也容易得多。

## 四、一个真实对照：把会议录音转写稿整理成研发纪要

拿日常研发里最常见的场景来对比一下。假设你刚开完一场产品评审会，手里有一份 3000 字的语音转写稿，需要整理成发给研发团队的执行纪要。

### 常见写法

> 帮我把下面这段会议记录总结一下，专业一点，条理清晰，不要太长，别漏掉重点。
>
> （后面直接粘贴 3000 字转写稿）

这么写出来的纪要，通常会分成“会议背景、核心讨论、未来展望”几大块，把闲聊总结成“各方就体验优化交换了意见”，而研发最关心的“哪个需求这期不做”“接口字段周几冻结”却经常被淹没在段落里。

### 按五步法重写后的版本

```xml
<role>
你是技术项目经理，负责把口语化的评审讨论整理成清晰的研发执行纪要。
</role>

<context>
这份纪要会直接发到研发和测试群，作为本周排期和开发的对齐依据。大家只关心拍板了什么、谁负责、什么时候交付、哪些需求明确不做，不需要客套的会议流水账。
</context>

<rules>
1. 只记录达成一致的结论和行动项；被否决的提议或没聊出结果的发散讨论，放到“待确认”或直接略过。
2. 每条行动项尽量写清负责人和截止时间；如果原文没提，写“待确认”，不要自行推测。
3. 直接陈述动作和结果，不用“进行了深入交流”“达成广泛共识”这类修饰语。
</rules>

<output_format>
严格按以下四个二级标题输出，全文控制在 600 字以内：
## 一、已拍板结论（最多 5 条）
## 二、明确不做或延期的需求
## 三、行动项（格式：事项 | 负责人 | 截止时间）
## 四、待确认事项
</output_format>

<example>
<input>
小王说支付弹窗要不要加个倒计时，老李说这期工期太紧来不及，下期再说吧，大家说行。然后前端小红问订单状态字段是不是周五前定死，后端阿强说没问题周四下午给文档。
</input>
<output>
## 一、已拍板结论
- 订单状态字段定义由后端在周四下午前出文档冻结。

## 二、明确不做或延期的需求
- 支付弹窗增加倒计时：本期工期紧张，延期至下期迭代。

## 三、行动项
- 输出订单状态字段接口文档 | 阿强 | 本周四下午

## 四、待确认事项
- 暂无
</output>
</example>

<transcript>
{{在此粘贴原始会议语音转写稿}}
</transcript>
```

这个版本之所以稳定，靠的是几处具体设计：`<context>` 说清了受众和用途；`<rules>` 提前堵住了编造负责人和截止时间的隐患；`<output_format>` 专门留出“明确不做”一栏，避免开发误做；`<example>` 用几十个字就定下了语言节奏；`<transcript>` 把杂乱原文收在最后，不干扰前面的指令。

## 五、日常聊天与工程上线，用两套不同节奏

有一点需要补充：不是每次打开对话框，都要写这么一整套 XML 结构。

如果只是平时查资料、写个小脚本、聊个想法，上来就写几百字规范反而低效。实际用下来，按场景分成两种节奏更舒服：

| 场景 | 适用方式 | 实用习惯 |
| :--- | :--- | :--- |
| **日常探索与对话** | 简短起步，多轮补齐 | 先用两三句直白的话交代目标和对象。如果需求比较复杂，可以在末尾加一句：“动笔前，先问我 3 到 5 个你觉得我没说清楚的关键问题。”让模型帮你把隐性前提问出来，比一个人闷头写长提示词省事。 |
| **写入代码的生产提示词** | 结构严密，评测驱动 | 分离 `developer` / `system` 与 `user` 角色，使用 XML/Markdown 分区与原生 JSON Schema；固定模型版本，攒 10 到 20 条覆盖边界情况和脏数据的样本做回归测试，每次改提示词都跑一遍对比。 |

日常对话其实是在帮需求“跑原型”。等某个高频任务跑顺了、踩过的坑都摸清了，再把它整理成结构化的固定模板，放进工作流或代码库里复用。

## 写在最后

把三家大厂的提示词指南通读下来，其实没有太多花哨的东西。XML 标签、角色分层、示例对齐、拆步流水线、评测集，背后指向的都是同一件事：把问题定义清楚，把边界说准，再根据结果一点点校准。

Paul Graham 在[《超越聪明》](/translations/smart/)里提到过，写作本身就是一种思考方式，很多想法是在写的过程里才理顺的。写提示词也一样。==一条提示词反复调不好，往往不是因为少背了某个技巧，而是我们自己对“到底想要什么”还没想透。==

下次觉得模型输出不合心意时，可以先停几秒问自己：如果对面坐着的是一位刚入职的聪明同事，我刚才说的这几句话，够不够让他一次把活干对？把这个问题答清楚，提示词多半也就写好了。
