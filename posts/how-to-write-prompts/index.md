# 如何写好一个提示词：读完三大厂官方指南后的实操笔记

![如何写好一个提示词手绘全览](/images/how-to-write-prompts/prompt-guide.webp)

前两年网上流传过不少“神级提示词”技巧，比如开头写“请你深吸一口气”“做好了给你 200 美元小费”，或者“你是一位拥有 30 年经验的世界顶级专家”。这些句子我以前也用过，甚至存进快捷短语里，提问前顺手粘贴一段。

放到现在的新模型上，这套做法的效果已经很有限。经常出现的情况是：写了一整页要求，末尾又补了五六条“不要太长”“不要说废话”“要有深度”，结果输出依然空洞，重点还是会漏。

前几天索性停下来，不再看二手总结，直接去读了三家模型厂商最新的官方文档：

- [Anthropic 官方 Prompt Engineering 指南](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)
- [OpenAI 官方 Prompt Engineering 指南](https://platform.openai.com/docs/guides/prompt-engineering)
- [Google Gemini 官方 Prompting Strategies 指南](https://ai.google.dev/gemini-api/docs/prompting-strategies)

三份文档合在一起看，里面并没有什么神秘技巧，讲的都是很具体的工程做法。对比之后也能看清，哪些原则在所有模型上都适用，哪些地方需要根据不同模型的特点分开处理。

---

## 一、三家官方文档的共同点与差异

虽然是三家不同的厂商，但在四个基础问题上，它们的建议高度一致：

- **把需求说清楚，比任何技巧都重要。** 平时给同事或外包安排工作，如果只说一句“帮我做一个好看点的页面”，交上来的结果大概率不符合预期。用大模型也是一样，背景是什么、给谁看、做到什么程度算完成，都要直接写明。
- **把指令和原始材料分开。** Anthropic 推荐使用 XML 标签（如 `<instructions>`、`<context>`、`<input>`），OpenAI 和 Gemini 常用 Markdown 标题或分隔线。用哪一种都可以，关键是不要把规则和大段待处理的文本混在同一段里，以免模型漏掉规则，或者被原文里的句子带偏。
- **工程接口尽量用原生结构化输出，不要只靠提示词约束 JSON。** 以前调接口时，总要在提示词末尾加一句“只返回合法 JSON，前后不要附带任何解释”。现在 OpenAI 和 Gemini 都原生支持 Structured Outputs，可以直接把 Pydantic 或 Zod 定义的 Schema 传给接口，在底层保证输出格式合法，提示词本身只需要关注内容质量。
- **靠测试集迭代，不要只试一次就定稿。** Anthropic 在总览页开头列了三个前提：先定义什么算成功、再准备验证方法、最后才优化初稿。OpenAI 也建议生产环境锁定具体的模型快照版本，并建立评测集（Evals）做回归测试，避免凭一次体感就上线。

比起共同点，三家文档的差异同样值得留意，拿同一套写法套所有模型有时会适得其反：

| 维度 | Anthropic（Claude） | OpenAI（GPT / 推理系列） | Google（Gemini） |
| :--- | :--- | :--- | :--- |
| **结构偏好** | 对成对的 XML 标签解析很稳定，支持多层嵌套 | 强调 `developer` / `system` 与 `user` 的角色权限分层 | 给出了明确的推荐顺序：角色 → 核心规则（最重要的放最前）→ 示例 → 输出格式 → 原始数据放最后 |
| **思维链（CoT）** | 复杂任务里可以让模型先在 `<thinking>` 中推演，再给最终答案 | **按模型区分**：普通模型可以细化步骤；自带内部思考链的推理模型，再写“请一步步思考”不仅多余，有时还会降低表现 | 深度推理与严格的 JSON 约束同时存在时容易互相影响，建议拆成两步完成 |
| **示例（Few-Shot）** | 建议用 `<example>` 提供 3 到 5 个覆盖不同情况的样本 | 使用推理模型时，建议先不给示例（Zero-Shot）直接测试；如果需要加示例，示例必须与规则完全一致，避免冲突 | 强调多个示例之间的格式保持一致（缩进、换行、标签不要变动），无关示例会分散注意力 |

读完三份文档有一个明显的感受：OpenAI 的文档最偏工程接口视角，Anthropic 更侧重把沟通方式讲透，Gemini 则把排版顺序和 Schema 用法写得很细。整体趋势是一致的：==模型能力越强，越不需要你去教它“怎么思考”，但越需要你把目标、边界和背景写准确。==

## 二、三个该改掉的旧习惯

对照文档复盘以前写的提示词，有三个习惯不仅没帮助，还经常降低输出质量。

### 1. 开头堆砌空洞的头衔

“你是拥有 20 年经验的顶级架构师 / 文案大师”，这类句子并没有告诉模型具体的判断标准。“顶级”既可以是克制简洁，也可以是华丽修辞，模型只能自己猜。

更好的写法是交代视角和读者。例如：“你负责给后端开发写接口文档。读者时间有限，只关心接口用途、参数边界和本地运行方式，不需要宣传性质的介绍。”字数相近，约束却明确得多。

### 2. 通篇写满“不要……”

以前看到输出不满意，我习惯在提示词末尾不断追加禁令：“不要用列表、不要太长、不要有翻译腔、不要写总结”。

只写“不要做什么”，模型仍然不知道你希望它怎么做。Anthropic 文档里举过一个直观的对比：与其写“不要用 Markdown 列表”，不如直接写“请用连贯的自然段落来写”。正面说明期望的做法，比列一排禁令更有效。

### 3. 把所有问题都寄希望于改提示词

Anthropic 专门写了一节说明“什么时候应该做提示词工程”。很多效果不佳的问题，并不是靠修改措辞就能解决的：模型缺少最新内部文档，应该接入检索（RAG）；单次任务步骤过多导致遗漏，应该拆成多步调用；响应慢或成本高，更换更轻量的模型通常比删减提示词更有效。

## 三、我现在写提示词的五个步骤

在日常写代码、整理资料和写文章时，遇到稍微复杂一点的任务，我现在基本按这五个步骤来组织提示词。

### 1. 先想清楚做到什么程度算合格

动笔前先确认三个问题：这份结果是给谁看的？满足哪两三条要求，我拿到后几乎不用大改？这件事里最不能接受的错误是什么（比如编造不存在的字段、漏掉边界条件、语气过于夸张）？

很多时候觉得模型输出不理想，是因为我们自己对结果的标准本来就模糊。

### 2. 用清晰分区隔开规则和原始材料

偏复杂的任务，我习惯按“先指令、后数据”的顺序写，用 XML 标签划清边界：

```xml
<role>
你当前的视角与职责
</role>

<context>
背景、目标读者、这份产出的实际用途
</context>

<rules>
1. 最关键的硬性要求放第一条
2. 尽量用正面描述说明“怎么做”
3. 原文里没有提到的信息直接标注“待确认”，不要自行补充
</rules>

<output_format>
明确结构、字数范围和语气
</output_format>

<input>
大段待处理的文本、代码或记录放最末尾
</input>
```

这套结构不只是方便模型解析。每次填写这五个区块时，自己也容易发现漏掉的前提，或者提前看出前后矛盾的要求。

### 3. 给关键要求补一句“为什么”

这是 Anthropic 文档里对我启发很大的一点。

平时提要求时，我们习惯只给一条硬规定，比如“文案控制在 30 字以内，不要用专业术语”。模型会机械地数着字数写，但对分寸和重点的把握往往不够好。

如果顺手补半句原因：“文案控制在 30 字以内，不要用专业术语，因为这句话会放在小程序首页的弹窗里，用户扫一眼只有两秒钟，看不懂就会直接关闭。”

加上使用场景后，模型不仅会控制长度，还会自动把最核心的信息放到前半句，把生硬的书面词换成常见表达。==交代清楚原因，往往比多加几条细则更有用。==

### 4. 少堆形容词，直接给两段示例

在提示词里写“专业、自然、接地气、通俗但不肤浅”，这类形容词对真人来说也很难拿捏。

更直接的办法是找出两三段你自己满意的成品，放进 `<example>` 里让模型参照。需要注意两点：多个示例之间的格式保持一致；示例本身必须遵守上面定好的规则（不要上面要求不超过 100 字，示例却放了 300 字）。

### 5. 复杂任务拆成两步完成

如果一个任务同时要求“深入分析问题”和“按严格格式排版或提取数据”，放在同一轮对话里往往两边都做不好。

更稳妥的做法是拆开：第一步只让模型分析问题、列出要点；确认内容无误后，第二步再把这份结果发给它，专门负责调整语气、压缩篇幅或转换成目标格式。每一步只做一件事，出了偏差也更容易定位。

## 四、一个真实对照：把会议转写稿整理成研发纪要

开完产品评审会后，把几千字的语音转文字发给 AI 整理纪要，是研发日常里很常见的场景。

### 常见写法

> 帮我把下面这段会议记录总结一下，专业一点，条理清晰，不要太长，别漏掉重点。
>
> （后面直接粘贴 3000 字转写稿）

这么发出去，输出通常会分成“会议背景、核心议题、总结展望”几大块，把闲聊概括成“各方就体验优化交换了意见”，而研发最关心的“哪个需求这期不做”“接口字段周几冻结”反而容易被埋在段落里。

### 改写后的版本

```xml
<role>
你是技术项目经理，负责把口语化的评审讨论整理成清晰的研发执行纪要。
</role>

<context>
这份纪要会直接发到研发和测试群，作为本周排期和开发的对齐依据。大家只关心拍板了什么、谁负责、什么时候交付、哪些需求明确不做，不需要客套的会议流水账。
</context>

<rules>
1. 只记录达成一致的结论和行动项；被否决的提议或没有定论的讨论，放到“待确认”中，不要把讨论过程当成结论。
2. 每条行动项写清负责人和截止时间；原文未提及就标注“待确认”，不要自行推测。
3. 直接陈述动作和结果，不使用“进行了深入交流”“达成广泛共识”这类修饰语。
</rules>

<output_format>
按以下四个二级标题输出，全文控制在 600 字以内：
## 一、已拍板结论（最多 5 条）
## 二、明确不做或延期的需求
## 三、行动项（格式：事项 | 负责人 | 截止时间）
## 四、待确认事项
</output_format>

<example>
<input>
小王说支付弹窗要不要加个倒计时，老李说这期工期太紧来不及，下期再说吧，大家说行。然后前端小红问订单状态字段是不是周五前定死，后端阿强说没问题周四下午给文档。
</input>
<output>
## 一、已拍板结论
- 订单状态字段定义由后端在周四下午前出文档冻结。

## 二、明确不做或延期的需求
- 支付弹窗增加倒计时：本期工期紧张，延期至下期迭代。

## 三、行动项
- 输出订单状态字段接口文档 | 阿强 | 本周四下午

## 四、待确认事项
- 暂无
</output>
</example>

<transcript>
{{在此粘贴原始会议语音转写稿}}
</transcript>
```

改写之后，同样一段 3000 字的转写稿发进去，输出稳定性会高很多：受众和用途写清楚了，编造负责人和截止时间的隐患提前堵住了，还单独列出了“明确不做”这一栏来减少沟通误会，底下的简短示例也让行文风格有了直接参照。

## 五、日常对话与工程上线，分开处理

平时查资料、写个小脚本，没有必要每次都套用一整套 XML 结构，那样沟通成本反而过高。按场景分成两种方式更实用：

| 场景 | 适用方式 | 常用习惯 |
| :--- | :--- | :--- |
| **日常对话与探索** | 简短起步，多轮补充 | 先用两三句直白的话说清目标和对象。遇到比较复杂的需求，可以在末尾加一句：“动笔前，先问我 3 到 5 个你觉得我还没说清楚的问题。”让模型反过来提问，通常比自己一次写完长要求更省力。 |
| **写进代码的生产提示词** | 结构严密，测试驱动 | 分离 `developer` / `system` 与 `user` 角色，使用 XML 或 Markdown 分区，格式交给原生 JSON Schema；锁定模型版本，准备 10 到 20 条包含边界情况和脏数据的样本做回归测试，每次改动都跑一遍对比。 |

日常对话相当于帮需求做验证。等某个高频任务跑顺、常见边界都摸清之后，再把它整理成固定模板放进工作流或代码库里。

## 结语

Paul Graham 在[《超越聪明》](/translations/smart/)里提到过，很多想法在动笔之前其实是模糊的，写着写着才理清楚。写提示词也类似。==一条提示词反复改还是不满意，多半是因为我们自己对“到底想要什么”还没想透。==

下次觉得模型输出不合心意时，可以先停下来想一个简单的问题：如果我现在把刚才那段话发给身边的同事，他能一次把事情做对吗？如果连同事都需要追着问三遍，问题通常不在模型身上。
