# 如何写好一个提示词：审视三大厂官方指南后的实战心法

![如何写好一个提示词手绘全览](/images/how-to-write-prompts/prompt-guide.webp)

如果你这两年重度使用大模型，收藏夹里八成躺过几篇标题惊悚的文章：《100 个神级 Prompt 咒语》《多加这一句话，让 AI 智商直接翻倍》《顶级工程师私藏提示词模板》。点进去一看，满屏都是“请你深吸一口气”“如果做好了我会给你 200 美元小费”“你现在是一位拥有 30 年经验、拿过图灵奖的世界顶级专家”。

我以前也信过这套，甚至煞有介事地把一长串“神级起手式”存进快捷短语里。可真到了手头干正事的时候，往往满头大汗地写了一整页玄学咒语，模型吐出来的依然是一段四平八稳、满嘴官腔、偏题十万八千里的“AI 味废话”。你越改越急，往里疯狂追加“严禁胡说”“务必深刻”“不要废话”，结果输出质量反而越调越崩。

痛定思痛之后，我决定把网上二手转述的玄学全都扔进垃圾桶，老老实实把目前最权威的三份一手文档从头到尾啃了一遍：

- [Anthropic 官方 Prompt Engineering 指南](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)
- [OpenAI 官方 Prompt Engineering 指南](https://platform.openai.com/docs/guides/prompt-engineering)
- [Google Gemini 官方 Prompting Strategies 指南](https://ai.google.dev/gemini-api/docs/prompting-strategies)

读完之后，我最大的感受并不是“学到了什么隐藏黑魔法”，而是一种酣畅淋漓的祛魅感。把三家大厂的文档摊在同一张桌子上交叉比对、逐条审视，你会清晰地看见：**哪些是跨越所有模型的真正底牌，哪些是各家模型性格带来的暗中分歧，又有哪些曾经被奉为圣经的老套路，今天已经彻底过时、甚至正在拖你的后腿。**

这篇文章不打算当官方文档的复读机，而是把这场“三方会审”后的思考彻底揉碎，变成一套我自己每天都在用、你看完立刻能上手的写提示词心法。

## 一、先做一场“三方会审”：大厂们的共识与分歧

把 Anthropic、OpenAI、Google 三家放在一起看，其实特别有意思。它们在底层工程哲学上高度一致，但在具体打法上又各自带着鲜明的“脾气”。

### 1. 三家不约而同押注的四大共识

第一，清晰度碾压一切技巧。三家文档在最显眼的位置都在反复强调同一个朴素真相：==写提示词的本质不是对模型念咒语，而是把一件任务交给一位极其聪明、博学多才，但刚入职第一天、完全不了解你团队背景和暗语的新同事。== 你跟这位新同事说话含糊其辞，他自然只能按全网最平庸的大路货标准来猜你的心思。

**第二，必须把“指令”和“材料”物理隔开。** 无论是 Anthropic 力推的 XML 标签（`<instructions>`、`<context>`、`<input>`），还是 OpenAI 和 Gemini 推荐的 Markdown 标题与分隔符，核心目的只有一个：别把你的要求、背景知识和待处理的原始文本混成一锅粥。一旦混在一起，模型不仅容易漏看要求，还极易被原始文本里夹带的语句带偏方向。

**第三，放弃用嘴求格式，拥抱原生结构化输出。** 两年前大家写代码调用模型，总要在提示词末尾撕心裂肺地喊：“只输出合法 JSON！绝对不要在前后加 markdown 代码块！不要解释！”如今 OpenAI 和 Gemini 官方都明确指向了同一个解法：在工程场景里，直接把 JSON Schema（如 Pydantic 或 Zod 定义）传给 API 的 Structured Outputs 能力，让模型在底层解码阶段严格受限，把提示词的宝贵精力留给真正的思考质量。

**第四，好提示词不是“写”出来的，是“测”出来的。** Anthropic 在总览页第一段《Before prompt engineering》就先泼了一盆冷水：在动手优化任何提示词之前，你得先搞清楚三件事，什么是你的成功标准、你有没有可复现的测试方法、以及你手里有没有一版初稿。OpenAI 同样把“锁定生产环境模型快照”和“建立自动化评测集（Evals）”写成了头等建议。靠肉眼试跑一次觉得“好像还行”，在严肃任务里几乎一定会翻车。

### 2. 藏在字里行间的三大分歧（看懂才不踩坑）

比共识更有价值的，其实是三家之间的差异。如果你拿着一套老模板无脑套用所有模型，很容易撞上暗礁：

| 维度 | Anthropic（Claude） | OpenAI（GPT / 推理系列） | Google（Gemini） |
| :--- | :--- | :--- | :--- |
| **结构偏好** | 极度偏爱成对的 XML 标签，擅长解析层级嵌套的标签容器 | 强调 `developer` / `system` 与 `user` 角色权限分离，配合 Markdown 与分隔符 | 给出了明确的**排版顺序建议**：角色 → 核心规则（最重要的放最前）→ 示例 → 输出格式 → 原始输入放最后 |
| **思维链（CoT）** | 复杂逻辑下鼓励用 `<thinking>` 标签让模型先推演再作答 | **明确区分模型类型**：普通模型可细化步骤，但对自带深度思考的推理模型，硬写“请一步步思考”**不仅多余，反而可能降低表现** | 复杂逻辑推理与严格 JSON 强约束并存时，容易互相牵制，建议拆成“先自由推理、再结构化提取”两步 |
| **示例（Few-Shot）** | 推崇用 `<example>` 包裹 3 到 5 个多样化示例来精准定调 | 面对强推理模型建议**先 Zero-Shot 裸跑**，非必要不加示例；若加，示例必须与规则 100% 一致，否则会让模型陷入逻辑冲突 | 极度强调示例之间的**格式绝对统一**（缩进、换行、标签一个标点都别乱变），且只放高度相关的示例 |

看到这里，你大概已经发现了一个极其反直觉的事实：**模型越聪明，越不需要你去“教它怎么动脑子”，但越需要你把“目标、边界和背景”交代干净。**

## 二、三个已经过时、甚至正在害你的“老黄历”

审视完三家官方指南，有三个在网上流传极广的习惯，我建议你今天起彻底戒掉。

### 1. 堆砌毫无信息量的浮夸人设

很多人写提示词第一句永远是：“你是一位拥有 20 年经验、精通心理学和营销学的世界顶级文案大师。”

冷静想一想，这句话除了让你自己心里觉得很厉害，到底给了模型什么有效信息？“顶级大师”的标准是什么？是像鲁迅那样犀利，像王小波那样幽默，还是像苹果发布会那样极简？你什么都没说。

真正有用的人设设定，从来不是吹嘘头衔，而是**框定观察视角、目标读者与取舍优先级**。比如把上面那句话改成：“你是一名长期给 B 端开发者写技术文档的主编。你的读者讨厌空洞的营销黑话，只关心这套方案到底解决什么痛点、有哪些边界限制以及怎么 5 分钟跑起来。”同样是一两句话，信息密度天差地别。

### 2. 一连串“不要……严禁……绝不……”的否定轰炸

这是我过去犯得最多的错。每次看到 AI 写得不对劲，我就往提示词里补一条禁令：“不要用排比句、不要用总而言之、不要写得像机器人、不要用列表、不要太长……”

心理学里有个经典的“粉红色大象效应”：一旦我命令你“千万不要想象一头粉红色大象”，你脑子里瞬间蹦出来的全都是粉红色大象。大语言模型的注意力机制也带着类似的毛病。Anthropic 官方指南就特别点破了这一点：==与其告诉模型“不要做什么”，不如直接告诉它“应该做什么”。==

与其写“不要使用 Markdown 无序列表和加粗小标题”，不如直接写“请用自然流畅的连贯散文段落来组织全文，段与段之间依靠逻辑自然衔接”。正面指令给出的是一条清晰的道路，而负面禁令只是在满地插满红牌，却没告诉模型到底该往哪儿走。

### 3. 试图用一段神级提示词解决所有工程问题

Anthropic 在文档里专门辟出一节讨论《什么时候该做提示词工程》（When to prompt engineer），这句话非常值得贴在显示器边上：不是每一个效果不好、延迟太高或成本太贵的问题，都应该靠改提示词来硬扛。

如果你的任务需要查阅公司内部不断更新的文档，死磕提示词不如先接好检索（RAG）；如果你的任务既要做深度代码审计，又要按极其苛刻的格式输出报表，把所有要求塞进同一轮提示词里互相打架，不如直接拆成两步流水线（Prompt Chaining），第一步专心找漏洞，第二步专心做格式整理；如果你只是觉得响应太慢，换一个轻量级高速模型往往比删减 200 字提示词管用十倍。

## 三、沉淀为我的实战心法：五步写出扛打的好提示词

聊完批判与祛魅，落回到日常真实工作里：当我现在打开对话框或者写一条系统提示词时，我脑子里到底是怎么一步步把它搭起来的？

我把三家大厂的精华浓缩成了五个动作，亲测在写文章、做技术方案、写代码和搭建自动化工作流里全都极其顺手。

### 第一步：先定“验收标准”，再敲第一个字

写提示词之前，先花三十秒问自己三个问题，别急着把模糊念头直接丢给 AI：

1. **这份产出是给谁看的？**（给老板做决策、给小白做科普、还是给线上程序直接解析？）
2. **做到哪三条，我拿到手不用大改就能直接用？**
3. **我最怕它在这件事上犯什么错？**（是瞎编数据、遗漏边界条件，还是语气过于浮夸？）

只要这三个问题想清楚了，你的提示词就已经赢过 80% 的人了。很多时候我们嫌 AI 笨，其实只是因为我们自己心里压根没想明白“好”到底长什么样，指望 AI 替我们把模糊的直觉猜准。

### 第二步：把“规则”与“原材料”结构化隔离

不管你用哪家模型，我强烈建议养成用清晰区块写复杂提示词的习惯。参考 Gemini 的“先指令后数据”顺序和 Anthropic 的 XML 标签法，一套极其稳健的骨架长这样：

```xml
<role>
你当前的视角与职责
</role>

<context>
这件事的背景、受众，以及为什么要做这件事
</context>

<rules>
1. 最核心的硬性要求放最前面
2. 尽量用“请做 X”代替“不要做 Y”
3. 遇到信息不足时，直接指出缺口，严禁自行编造
</rules>

<output_format>
明确交代输出结构、字数体量与语气风格
</output_format>

<input>
把大段待处理的原始文本、代码或会议记录放在最末尾
</input>
```

这套结构之所以好用，不只是因为模型解析起来毫无歧义，更因为它**倒逼着你自己把脑子里的需求理顺**。每次填完这五个标签，你经常会惊讶地发现：原来刚才漏掉了一个关键背景，或者有两条规则自己就自相矛盾。

### 第三步：给关键规则多补一句“为什么”

这是我在读 Anthropic 官方指南时拍案叫绝的一条洞察。

大多数人写约束时喜欢下干巴巴的死命令，比如：“输出文本里绝对不要出现省略号和奇怪的符号。”模型确实会尽量照做，但一旦遇到边角情况（比如破折号、星号、括号里的英文缩写），它根本不知道该不该保留，因为你只给了规则，没给动机。

但只要你顺手多补半句理由：“请不要使用省略号、星号或生僻缩写，**因为这段文字稍后会直接送进语音合成引擎（TTS）朗读给听众听**。”

奇迹就发生了。现代大模型具备极强的泛化理解能力，一旦它明白了背后的真实用途与动机，它就会自动站到你的立场去审视全文：不光避开省略号，还会顺手把拗口的长难句拆短，把不适合念出来的表格改成自然口语。==交代清楚“为什么”，等于把一条死板的正则规则升级成了一套活的判断原则。==

### 第四步：与其堆砌十个形容词，不如甩出两个标杆示例

我见过太多人在提示词里这样形容文风：“请写得专业又不失幽默、高级又接地气、深刻但通俗易懂、有网感但别太轻浮。”

说实话，别说 AI 了，把这十六个字交给一个拿过普利策奖的真人记者，他也得挠头半天不知道你到底想要啥。形容词是极其廉价且充满歧义的。

真正一击必杀的办法，就是 **Few-Shot（少样本示例）**。挑出两三段你自己最满意的真实成品，用 `<examples>` 标签原封不动地贴进去，告诉模型：“这就是我想要的节奏、颗粒度和语气，请照着这个标准处理接下来的输入。”

记住 OpenAI 和 Gemini 共同提醒过的两个细节：第一，**示例的格式必须彼此严格统一**，别第一个示例用项目符号、第二个示例改成数字编号；第二，**示例和上面的规则绝不能打架**，别在规则里写“控制在 100 字以内”，结果下面贴的范例自己就写了 300 字，这会让擅长严谨推理的模型当场陷入自我怀疑。

### 第五步：复杂任务别贪心，学会拆成“两段式流水线”

哪怕到了今天，让模型在单次回复里同时完成“深度发散分析 + 挑错批判 + 严格排版 + 精准 JSON 提取”，依然很容易顾此失彼。

当你发现一条提示词越写越长、补丁打了一层又一层还是不稳时，别再往里硬塞要求了，立刻把它拆开：

- **第一轮专注“思考与内容”**：让模型放开手脚做分析、列漏洞、提方案，甚至先让它把不确定之处反问出来，由你拍板确认。
- **第二轮专注“加工与定型”**：把第一轮确认好的干货作为 `<input>` 喂进去，专门负责润色语气、精简篇幅或转成标准格式。

拆成两步之后，每一步的目标都极其纯粹，不仅产出质量暴涨，出了问题你还能一眼定位到底是“思考环节偏了”还是“表达环节歪了”。

## 四、真实对照：一条“烂提示词”是如何脱胎换骨的？

光讲道理不过瘾，咱们拿一个职场和研发里最常见、也最容易翻车的真实场景来做一次手术：**把一段长达几千字、七嘴八舌的产品评审会议转写稿，整理成发给研发团队看的执行纪要。**

### 反面教材：90% 的人随手发出去的写法

> 帮我把下面这段会议记录总结一下，要专业一点，条理清晰，不要太长，别漏掉重点。
>
> （后面直接粘了一坨 3000 字的语音转写文本）

你闭着眼睛都能猜到 AI 会吐出什么东西：一长篇毫无灵魂的“会议背景 / 讨论要点 / 总结展望”，把大家随口闲聊的废话一本正经地总结成“各方就用户体验进行了深入探讨”，却偏偏把“后端接口周五前必须冻结字段”和“某项需求决定砍掉不做”这种要命的结论埋在第三段角落里。

### 最佳实践：融合三家指南后的生产级写法

现在，我们用前面的五步心法把它彻底重构一遍：

```xml
<role>
你是一名经验丰富的技术项目经理，擅长从杂乱的口语讨论中提炼出无歧义的研发决策。
</role>

<context>
这份纪要会直接发到研发与测试大群里，作为本周迭代排期与开发的唯一对齐依据。大家时间都很紧张，没人想读客套的会议流水账，只关心“拍板决定了什么、谁负责、什么时候交付、还有什么悬而未决的风险”。
</context>

<rules>
1. 只提取明确达成共识的结论和行动项；大家随口发散、最终被否决或没有定论的闲聊，一律归入“未决/挂起事项”或直接忽略，不要把讨论过程当成结论。
2. 每一条行动项必须尽量标明【负责人】和【截止时间】；如果原始记录里没提到，明确标注“待确认”，严禁自行脑补编造。
3. 使用简洁直白的工程语言，直接陈述动作与结果，避免使用“进行了充分探讨”“达成了广泛共识”这类空洞修饰语。
</rules>

<output_format>
请严格按以下四个二级标题输出，总字数控制在 600 字以内：
## 一、已拍板结论（最多 5 条）
## 二、明确不做或延期的需求（防止开发误做）
## 三、行动项清单（格式：事项 | 负责人 | 截止时间）
## 四、待确认风险与卡点
</output_format>

<example>
<input>
小王说支付弹窗要不要加个倒计时，老李说这期工期太紧来不及，下期再说吧，大家说行。然后前端小红问订单状态字段是不是周五前定死，后端阿强说没问题周四下午给文档。
</input>
<output>
## 一、已拍板结论
- 订单状态字段定义由后端在周四下午前出文档冻结。

## 二、明确不做或延期的需求
- 支付弹窗增加倒计时功能：因本期工期紧张，延期至下期迭代。
```

## 五、进阶一格：日常对话 vs 工程上线的两套节奏

写到这里，还有一个特别容易让人走极端的地方必须点破：**不是每次跟 AI 聊天，你都得先画一套 XML 五件套。**

如果只是平时查资料、聊灵感、写个小脚本，一上来就憋一篇八百字规格书，反而把沟通成本搞得比自己干还高。根据场景不同，我手里其实分成两套截然不同的节奏：

| 场景 | 适用打法 | 关键技巧 |
| :--- | :--- | :--- |
| **个人日常对话与探索** | **轻量起步，多轮校准** | 先用两三句直白的话交代目标和受众；遇到复杂需求，直接补一句：“在正式动笔前，先向我反问 3 到 5 个你觉得最关键、我还没说清楚的问题。”让 AI 帮你把隐性需求挖出来，比你一个人闷头写长提示词省力十倍。 |
| **固化工作流与代码上线** | **结构严密，评测驱动** | 使用角色隔离（`developer` / `system` 与 `user` 分离）、XML/Markdown 清晰分区、原生 JSON Schema 约束输出；锁定具体模型版本，准备 10 到 20 条覆盖真实脏数据与边界情况的测试用例（Evals），每次修改提示词都跑一遍回归对比。 |

你会发现，这两套节奏并不冲突：**日常对话是你在帮提示词“探索原型”，一旦某个高频任务跑顺了、摸清了所有坑点，再把它沉淀成上面那种结构化的工程模板。**

## 写在最后：好提示词的尽头，是清晰思考的能力

通读完 Anthropic、OpenAI 和 Google 三家大厂的提示词工程文档，又回头复盘了自己踩过的无数坑，我越来越确信一件事：

这个世界上从来没有什么能让平庸想法一键变魔术的“秘籍咒语”。那些看似高级的技巧（XML 标签、角色分层、Few-Shot、Prompt Chaining、Evals），剥开外壳之后，指向的其实全都是同一门古老的手艺：**清晰地定义问题、准确地表达边界、以及用真实反馈持续校准结果。**

在[《超越聪明》](/translations/smart/)里，Paul Graham 说过一句让我印象极深的话：写作本身就是一种思考方式，不是先想透了再写，而是写着写着才真正想透。今天放在提示词上，其实一模一样。==写不好一条提示词，十有八九不是因为你漏背了某个神秘模板，而是因为你自己脑子里对“到底想要什么”还是一团迷雾。==

下一次觉得 AI 听不懂人话、产出让人抓狂的时候，不妨先停下来别急着骂模型，也别急着去网上搜新咒语。把屏幕关掉三十秒，问问自己：如果对面坐着的是一位刚入职的顶级聪明同事，我刚才那两句话，真的足以让他一次把活干漂亮吗？

当你开始用这种眼光写下每一行提示词，AI 突然就会变得前所未有地聪明、听话且锋利。
