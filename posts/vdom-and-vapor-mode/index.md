# 为什么技术总爱走回头路

![为什么技术总爱走回头路](/images/vdom-and-vapor-mode/cover.webp)

在技术圈待久了，很容易注意到一个现象：不少让人眼前一亮的新方案，绕了一大圈之后，长得特别像十年前被淘汰掉的旧做法。

前端尤其如此。

十多年前，大家用原生 API 或 jQuery 直接改页面上的真实 DOM。后来 React 和 Vue 带着虚拟 DOM 流行起来，几乎成了行业默认选项。可到了今天，Vue 又推出“蒸汽模式（Vapor Mode）”，把虚拟 DOM 撤掉，重新回到直接操作真实 DOM。

写样式也走过一样的路。早年大家直接把样式写在 HTML 标签上；后来行业形成共识，结构和样式必须分开；到了今天，以 Tailwind 为代表的原子化 CSS 普及开来，大家又把一长串样式类名写回了 HTML 标签里。

单看表面，这些变化都很像在开倒车。

但退回当时的处境仔细看，会发现它们并不是在原地打转。工程里极少有哪一项指标拿满分的方案，所谓的“最优解”，都是在当时的条件下权衡利弊后的妥协。

## 只差一个中间层

不管框架怎么设计，浏览器最终只做一件事：修改真实 DOM。你点一下按钮，页面上的数字从 `1` 变成 `2`，背后一定有一次对真实 DOM 的改动。

数据变了，页面怎么跟着变？虚拟 DOM 和蒸汽模式的差别，就在于中间要不要多加一层：

![只差一个中间层：虚拟 DOM 与蒸汽模式对比](/images/vdom-and-vapor-mode/vdom-vs-vapor.webp)

多出这一层，既占内存，又要花时间比对。十年前的框架作者并不傻，当年为什么非加不可？

## 当年为什么非加不可

站在今天回头看十年前的方案，很容易觉得它笨重、绕弯。

但如果把时间拉回 2013 年，回到那个到处都在用 jQuery 手写 DOM 的年代，事情就很清楚了：手写原生 DOM 一定比虚拟 DOM 快。既然如此，当年大家放弃原生写法、转向虚拟 DOM，追求的就一定不是“更快”。

网页从静态展示变成复杂应用之后，最先失控的往往不是性能，而是代码维护。改一个购物车数量，你得手动去改顶部角标、单行小计、总价、满减提示和结算按钮，漏改一处就是 Bug。人写代码时最希望的是：我只管写清楚“数据长这样时，页面该长什么样”，至于从旧状态怎么一步步改过去，交给框架去算。

想省心其实有个粗暴办法：数据一变，把整块页面推倒重写（比如直接替换 `innerHTML`）。可这太慢了，而且输入框焦点、滚动条位置全会丢。所以大家需要一个折中方案：不求跑出极限手写的速度，只要比全量重写快得多，保证绝大多数页面流畅就行。

除此之外，真实业务里的界面经常高度动态，同一个组件可能根据权限和配置拼出完全不同的结构；后来服务端渲染（SSR）、原生 App、小程序陆续出现，也需要一层统一的中间表达，把“描述界面”和“最终画到哪个平台”分开。

更重要的是当时的工具条件。十年前的构建工具和编译器远没有今天这么强，没法在打包阶段就把模板依赖静态分析清楚。事前算不出来，就只能在代码跑起来以后，靠一层中间层在运行时处理。

把这几件事放在一起看，当年其实没有别的选择：直接手写原生 DOM，速度最快，但业务一复杂人就管不过来；每次全量重绘，写起来最省事，但页面根本没法用。虚拟 DOM 在运行效率上退了一步，却同时接住了声明式写法、足够流畅的体验、动态与跨端需求，也符合当时的编译条件。

==没有哪一项做到 100 分，但把几件事综合算下来，虚拟 DOM 就是当年得分最高的妥协。==

今天之所以出现蒸汽模式，是因为当年逼着大家妥协的那个条件变了。现代编译器在打包前已经能把大多数模板里的静态部分和动态绑定拆得清清楚楚，细粒度响应式也可以把数据变化直接通知到某一个文本节点或属性。既然 80% 以上的常规页面在运行前就能算明白，再留着虚拟树反复比对，这层中间层就成了多余的开销。

蒸汽模式本身同样带着妥协。它能跑得这么轻，前提是代码要遵守模板的静态约束，让编译器提前看得穿。一旦遇到高度动态、打包前预测不了结构的渲染逻辑，蒸汽模式也处理不了，还是得退回虚拟 DOM。所以 Vue 并没有删掉虚拟 DOM，而是允许两者在同一个项目里混用：结构确定的地方撤掉中间层换效率，高度动态的地方留着中间层换灵活。

## Tailwind 也在“开倒车”？

虚拟 DOM 不是孤例，原子化 CSS（比如 Tailwind）走过的几乎是同一条路。

Tailwind 刚流行起来时，很多写惯传统 CSS 的前端看一眼代码就会皱眉：一个 `<div>` 上写着 `flex items-center p-4 text-sm text-gray-600`，这和二十年前大家嫌弃的行内样式（inline style）有什么区别？

要理解为什么当年必须把样式拆出去，同样得回到二十年前。

那时候还没有“组件化”这个概念。一个网站几十个 HTML 文件，如果把样式直接写在标签上，哪天要把全站按钮的圆角从 4px 改成 6px，就得去几十个文件里逐一修改。再加上当时没有统一的设计规范，你写 `padding: 7px`，我写 `padding: 9px`，时间一长样式就会失控。

在当时的条件下，最稳妥的折中办法是在 HTML 和样式之间加一层“语义化类名”的中间层：标签里只写 `<button class="btn-primary">`，具体样式全收进外部 CSS 文件集中管理。后来的 BEM、Sass、CSS Modules，都是在完善这层中间层。

可到了今天，逼着大家拆分样式的条件全都变了。现在大家复用的单位是 `<PrimaryButton />` 这样的组件，不再靠一个类名去跨几十个 HTML 文件复用；原子化类名把间距、字号和色阶提前限定在了统一的设计规范里，不再是早年那种随意填像素值的行内样式；构建工具在打包时还能自动扫描实际用到的类名，把没用到的统统删掉，最终产出的 CSS 反而更小。

条件变了之后，曾经用来保证整洁的“语义化类名中间层”，在很多项目里反而成了负担：写个普通容器都要费神想一个 `.card-wrapper-inner-box` 这样的名字，改个边距还得在两个文件之间来回切换。

原子化 CSS 表面上看像是回到了二十年前把样式写进标签的老路，实际上脚下的前提早就换了一遍。和蒸汽模式一样，它是在工具和工程条件成熟之后，撤掉了当年不得不加的一层中间层。

## 回到现实：该留还是该拆

快了几毫秒、少起了几个类名，其实只是技术演进里最外层的变化。

跳出代码回到现实，我们几乎每天都在面对同一个判断：公司里的审批流程、团队里的协作规范、商业里的中介代理，甚至自己早年立下的规矩，到底该留着，还是该拆掉？

做判断时最容易走偏的地方，是只盯着一个点下结论。嫌流程慢、手续多，就觉得旧规矩一无是处，恨不得全部砍掉；或者看到某个新做法表面上像老路，连前提都没看清就直接否定。

回到第一性原理，其实就问三个问题：

当年定下这套规矩，到底是为了挡住什么麻烦？不先搞清楚它解决过什么，拆掉大概率会踩回老坑。

留着要付什么代价，拆掉又要靠什么补位？没有两头占尽的方案，关键是想清楚自己愿意付哪一笔账。

当年逼着我们这么做的条件，今天真的变了吗？条件没变，强行拆掉就是开倒车；只有当工具、规则或能力真的跟上了，才到了撤掉它的时候。

## 绕回来，但不是原地

技术总爱“走回头路”，因为人一直都在找更直接、更少绕弯的办法。

只是每一次绕出去再绕回来，脚下的条件早已不是十年前的样子。看清约束，承认妥协，在当下做出综合最合适的那一个选择，大概就是第一性原理最实在的用法。
