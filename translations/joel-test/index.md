# 乔尔测试：通往优秀代码的 12 个步骤

> 原文：[The Joel Test: 12 Steps to Better Code](https://www.joelonsoftware.com/2000/08/09/the-joel-test-12-steps-to-better-code/) · 作者：Joel Spolsky（2000年8月9日） · [查看英文原版](./en.md)

![乔尔测试：通往优秀代码的 12 个步骤](/images/joel-test/joel-test.webp)

你听说过 [SEMA](http://www.sei.cmu.edu/sema/welcome.html)（注：卡内基梅隆大学软件工程研究所提出的软件能力成熟度评估体系，即 CMM 的前身分支）吗？那是一套极其深奥晦涩、专门用来评估软件团队有多优秀的测评体系。不，*等等！千万别点那个链接！* 光是把那套玩意儿看明白，就得花掉你整整六年青春。所以我干脆自己发明了一套极不负责任、极其糙快猛的测试表，专门用来给软件开发团队的质量打分。这套测试最棒的地方在于，全程只需要花大约 **3 分钟**。省下来的那六年光阴，你完全可以去读个医学院拿个医生执照了。

> ### 乔尔测试（The Joel Test）
>
> 1. **你们使用源代码版本控制吗？**（Do you use source control?）
> 2. **你们能一步完成构建（Build）吗？**（Can you make a build in one step?）
> 3. **你们每天都进行每日构建（Daily Builds）吗？**（Do you make daily builds?）
> 4. **你们有缺陷跟踪数据库（Bug Database）吗？**（Do you have a bug database?）
> 5. **你们会在写新代码之前先修完已知的 Bug 吗？**（Do you fix bugs before writing new code?）
> 6. **你们有一份实时更新的真实排期表吗？**（Do you have an up-to-date schedule?）
> 7. **你们在写代码前有产品设计规格文档（Spec）吗？**（Do you have a spec?）
> 8. **程序员拥有安静无打扰的工作环境吗？**（Do programmers have quiet working conditions?）
> 9. **你们使用金钱能买到的最好工具吗？**（Do you use the best tools money can buy?）
> 10. **你们有专职的测试人员吗？**（Do you have testers?）
> 11. **新候选人在面试时会被要求现场写代码吗？**（Do new candidates write code during their interview?）
> 12. **你们做走廊可用性测试（Hallway Usability Testing）吗？**（Do you do hallway usability testing?）

“乔尔测试”最妙的地方在于，每一道题都能极其干脆地给出**“是（Yes）”**或**“否（No）”**的回答。你根本不需要去统计什么“人均日产代码行数”或者“每个拐点的平均缺陷率”。每回答一个“是”，就给你们团队加 1 分。当然，“乔尔测试”也有个小瑕疵：你*千万别*拿它去检验核电站控制软件的安全性。

==**满分 12 分代表完美，11 分尚可容忍，但如果只拿到 10 分或更低，你们团队就已经深陷严重的危机之中了。**== 残酷的现实是，市面上绝大多数软件团队常年都在以 2 到 3 分的惨状裸奔，他们急需一场刮骨疗毒的拯救，因为像微软这样的顶级软件公司，是全天候满负荷维持在 12 分水准上运转的。

当然，这 12 条并非决定商业成败的唯一因素：尤其是假如你有一支满分的顶级研发团队，却在埋头苦干一款根本没人想要的产品，那市场照样不会买账。你也可以想象出一支由天赋异禀的“独行快枪手（gunslingers）”组成的草台班子，上面这 12 件事他们一件都不干，却依然靠个人英雄主义搓出了改变世界的惊艳软件。但是，在其他条件相同的情况下，只要你能把这 12 件事全部做对，你手头就拥有了一支纪律严明、能够持续稳定交付高质量软件的铁军。

## 1. 你们使用源代码版本控制吗？

我用过商业收费的源码版本控制软件，也用过完全免费的 [CVS](http://www.cvshome.org/)（注：本文写于 2000 年，当时 Git 尚未诞生），说句公道话，免费的 CVS 就*完全够用了*。但如果你连源码版本控制都没有，想让几个程序员协同干活简直会让你崩溃到抓狂。程序员根本没法知道别人改了哪些代码，犯了错也没法轻松回滚。源码版本控制系统还有一个妙不可言的好处：完整的源代码会被检出（Check out）在每一位程序员自己的本地硬盘上。我这辈子还从没听说过哪个使用了版本控制系统的项目发生过大规模丢代码的惨剧。

## 2. 你们能一步完成构建（Build）吗？

我说的“一步完成构建”指的是：从最新的源码快照出发，直到生成最终可以直接发版交付的安装包，中间一共需要经历多少个手动步骤？在优秀的团队里，只需要运行**一行脚本命令**，系统就会自动从零完整拉取最新代码、重新编译每一行源码、根据各种版本号、多语言包和 `#ifdef` 宏定义组合生成所有的可执行文件（EXE）、自动打包生成安装程序，并直接输出最终的发布介质（无论是光盘镜像布局、官网下载页还是任何其他交付形态）。

==如果这个发版构建过程需要超过一个步骤，它就必然会沦为滋生低级错误的温床。== 越是临近正式发版的紧要关头，你就越需要具备极快的迭代闭环：修掉“最后一个”Bug、重新生成最终可执行文件、立刻验证。如果编译代码、运行安装包制作工具等全套流程需要人工操作 20 个步骤，你不仅会被逼疯，而且百分之百会犯下愚蠢的低级失误。

正是因为这个原因，我效力的上一家公司直接把安装包制作工具从 WISE 换成了 InstallShield：我们的*硬性要求*是，安装包构建过程必须能通过脚本在深夜由 Windows NT 定时任务自动无人值守跑完，而当时的 WISE 没法在后台定时任务里过夜自动运行，所以我们毫不犹豫地把它扔进了垃圾桶。（后来 WISE 团队那些热心的朋友向我保证，他们的最新版本已经支持夜间自动构建了。）

## 3. 你们每天都进行每日构建（Daily Builds）吗？

在使用源码版本控制时，偶尔会有某个程序员在提交代码（Check in）时不小心把整个构建给搞挂了（Break the build）。举个最常见的例子：他在本地新建了一个源文件，在他自己的电脑上编译运行一切正常，但他偏偏忘了把这个新文件添加（Add）进代码仓库里。于是他高高兴兴地锁上电脑下班回家了，浑然不觉自己闯了大祸；而团队里的其他所有人拉下代码后全都编译报错、没法干活，最后只能郁闷地跟着大眼瞪小眼。

“把构建搞挂”这件事危害极大（偏偏又极其常见），因此团队必须坚持做**每日构建（Daily Builds）**，确保任何破坏构建的提交都不会成为漏网之鱼。在大型研发团队里，确保构建报错能被立刻修复的一个绝佳实践，就是在每天下午（比如午饭时间）固定跑一次全量每日构建。大家在去吃午饭前把手里写好的代码尽可能提交上去；等吃完午饭回来，构建已经跑完了。如果构建成功，皆大欢喜！所有人拉取最新源码继续干活。如果构建挂了，闯祸的人立刻动手修复，而其他同事依然可以基于午饭前那个完好无损的构建版本继续正常开发。

当年我在微软 Excel 团队工作时，我们有一条铁律：==谁要是把每日构建给搞挂了，作为“惩罚”，他就必须一直充当构建系统的“全职保姆”盯守每一次构建，直到下一个倒霉蛋把构建搞挂为止。== 这不仅是一个让大家在提交代码前小心谨慎的绝佳威慑，更是一个让团队里每位成员轮流熟悉整套构建流程的绝妙机制。

关于每日构建的更多细节，可以阅读我的专文《[每日构建是你的好朋友](https://www.joelonsoftware.com/articles/fog0000000023.html)》。

## 4. 你们有缺陷跟踪数据库（Bug Database）吗？

我不管你怎么狡辩。只要你在写代码，哪怕整个团队只有你光杆司令一个人，如果手头没有一个条理清晰的数据库把代码里所有已知的 Bug 统统记录在案，你最终交付出来的就一定是烂代码。很多程序员迷之自信地觉得自己能把所有 Bug 清单全记在脑子里。纯属扯淡！我脑子里同时连两三个以上的 Bug 都记不住，只要睡一觉到第二天早上，或者赶上发版前焦头烂额的冲刺期，那些没记下来的 Bug 就会被忘得一干二净。你绝对必须用正式的流程把每一个 Bug 追踪起来。

缺陷跟踪数据库可以做得很复杂，也可以极其简单。一个最精简但实用的 Bug 数据库，针对每一条缺陷必须包含以下 5 项核心信息：

- **完整重现该 Bug 的操作步骤**（Complete steps to reproduce the bug）
- **预期的正常行为**（Expected behavior）
- **实际观察到的错误行为**（Observed buggy behavior）
- **当前指派给谁处理**（Who it's assigned to）
- **是否已经修复**（Whether it has been fixed or not）

如果仅仅是因为嫌弃市面上那些缺陷管理软件太繁琐，才导致你迟迟没有追踪 Bug，那你哪怕立刻拉一张只有这 5 列的简单表格，也请*马上用起来*。

关于缺陷跟踪的更多实践，请阅读《[无痛缺陷跟踪指南](https://www.joelonsoftware.com/articles/fog0000000029.html)》。

## 5. 你们会在写新代码之前先修完已知的 Bug 吗？

微软历史上第一版 Windows 平台下的 Microsoft Word 项目，是软件工程史上出了名的“死亡行军（Death March）”项目。那个项目仿佛永远写不完，工期一拖再拖。整个团队天天加班到昏天黑地，发布日期推迟了一次、又一次、再一次，全员承受着令人窒息的高压。等那个该死的软件在延期了好几年之后终于艰难发版时，微软先把全员送到墨西哥坎昆度了个假，回来后立刻坐下来做了一场深刻到骨子里的复盘反思。

复盘得出的惨痛教训是：当时的项目经理们为了死保表面上的“进度排期表”，逼得程序员们只顾着火急火燎地往前赶功能，写出了一堆烂透了的代码，因为“修 Bug 阶段”压根没有被算进正式的开发排期里。没有任何人试图控制缺陷数量，甚至恰恰相反。坊间流传着这样一个真实段子：当年有一位程序员负责编写计算一行文本像素高度的函数，为了赶进度，他干脆在函数里直接写了一行 **`return 12;`**，然后心安理得地等着测试组以后提 Bug 报告说他的函数算得不准。整张项目排期表，简直沦为了一份“等待被转化为 Bug 的功能打卡清单”。在事后复盘报告中，这种荒唐的做法被戏称为**“无限缺陷开发法（Infinite Defects Methodology）”**。

为了彻底根治这一顽疾，微软在全公司范围内全面推行了**“零缺陷开发法（Zero Defects Methodology）”**。当时公司里不少程序员听了都忍不住偷笑，觉得管理层简直是在痴人说梦，以为靠发一道行政命令就能消灭 Bug。但实际上，“零缺陷”的真正含义是指：==在任何时刻，团队的最高优先级永远是**在动笔写任何一行新代码之前，先把所有已知的 Bug 统统修干净**。== 原因如下：

首先，**拖延修 Bug 的时间越长，修复它的代价（无论是时间成本还是金钱成本）就会呈指数级暴涨。**

- 举个例子，当你敲错了一个字母或犯了个语法错误，编译器当场报错拦住你，修掉它几乎不费吹灰之力。
- 当你写完一段代码第一次运行测试就看到了 Bug，你分分钟就能把它修好，因为那段代码的所有上下文逻辑在你脑子里还是热乎的。
- 如果你在几天前写的代码里发现了一个 Bug，你得花点工夫去排查定位，但只要重新读一遍自己写的代码，你很快就能回想起当时的思路，并在合理的时间内修好它。
- 但如果你是在*几个月前*写的代码里发现了一个 Bug，关于那段代码的大量细节你早就忘到九霄云外去了，修起来会痛苦得多。更要命的是，那时候你可能是在修*别人*写的代码，而写出那段代码的仁兄此刻正躺在加勒比海的阿鲁巴岛沙滩上晒太阳度假呢！到了这种地步，修 Bug 就变成了一门考古与科研工作：你必须放慢脚步、小心翼翼、抽丝剥茧，而且你根本没法预估到底要花多久才能找到病根。
- 而如果这个 Bug 是在代码*已经正式发版交付给客户之后*才被发现的，那你为了修补它所付出的代价简直就是天文数字了。

这是必须立刻修 Bug 的第一个原因：越早修，耗时越短。

还有第二个同样致命的原因：**预测“写一段新代码要花多长时间”很容易，但预测“修一个现有 Bug 要花多长时间”几乎是不可能的。** 举个例子，如果我让你预估写一个列表排序函数需要多久，你能给出一个相当靠谱的估时。但如果我让你预估“为什么装了 IE 5.5 浏览器后我们的软件就崩了，修好这个 Bug 需要多久”，你甚至连*瞎猜*都没法猜，因为（根据定义）在修好它之前你压根不知道*到底是什么原因*导致了这个 Bug。查出病因可能需要整整三天，也可能只需要两分钟。

这意味着什么？==这意味着如果你的项目排期表里还攒着一大堆没修的陈年 Bug，那你的排期表就是一张废纸，毫无可信度可言。相反，如果你已经修光了所有**已知**的 Bug，剩下的工作全都是编写新代码，那么你的排期预测就会准得惊人。==

把已知 Bug 数量始终清零还有第三个巨大优势：**你能以快得多的速度对市场竞争做出反应。** 有些程序员把这种状态称为让产品在任何时刻都保持**“随时可发版（Ready to ship）”**的战备状态。一旦竞争对手突然祭出了某个抢走你客户的杀手级新功能，你可以立刻只把这个新功能写出来，然后当场发版上线反击，而根本不需要先花上几个月去清理堆积如山的历史欠账 Bug。

## 6. 你们有一份实时更新的真实排期表吗？

这就自然引出了排期表（Schedule）的话题。只要你们写的代码对公司业务哪怕有一丁点重要性，业务部门就有无数个理由迫切需要知道“代码到底什么时候能写完”。程序员群体向来对排期表充满怨气，一提排期就暴跳如雷：“写完的时候自然就写完了！”他们冲着业务人员大吼大叫。

遗憾的是，这种傲慢在商业世界里根本行不通。在代码正式发版之前，公司有太多商业决策必须提前很久做好筹备：客户演示、行业展会、广告投放、公关宣发等等。而让整个公司协同运转的唯一办法，就是制定一份排期表，并且让它始终保持**实时更新**。

拥有排期表的另一个核心价值在于：它会倒逼你决定这一版究竟要做哪些功能，更会倒逼你挑出那些最不重要的功能并**狠心把它们砍掉**，而不是任由项目滑向万劫不复的“[功能蔓延症](http://www.netmeg.net/jargon/terms/c/creeping_featuritis.html)（Featuritis，即需求范围失控膨胀）”。

维护排期表根本不需要搞得那么痛苦。不妨读一读我的文章《[无痛软件排期指南](https://www.joelonsoftware.com/articles/fog0000000245.html)》，里面介绍了一种极其简单就能做出高准确度排期表的方法。

## 7. 你们在写代码前有产品设计规格文档（Spec）吗？

==写产品设计规格文档（Spec）这件事，简直就像用牙线洁牙一样：人人都承认它是一件大好事，但偏偏没人真正去做。==

我也不太确定为什么会这样，但八成是因为绝大多数程序员骨子里都痛恨写文档。结果就是，当一支纯粹由程序员组成的团队去攻克某个问题时，他们本能地喜欢直接用代码来表达解决方案，而不是先写成文档。比起先坐下来写一份设计规格书，他们宁可一头扎进编辑器里直接开敲代码。

然而，在设计文档阶段，当你发现逻辑漏洞时，只需要改几行文字就能轻松搞定；一旦代码已经写出来了，修改问题的代价就会呈几何级数飙升，无论是心理抗拒成本（没人舍得扔掉自己辛辛苦苦写出来的代码）还是时间成本都高得吓人，结果大家就会本能地抗拒去真正修补设计缺陷。没有设计规格文档就直接开干的软件，最终往往会变成架构烂透的泥潭，开发进度也会彻底失控。网景（Netscape）公司当年似乎就栽在这个大坑里：他们的前四个浏览器版本在野蛮生长中变成了一团乱麻，以至于管理层最终做出了一项[愚蠢透顶的决定](https://www.joelonsoftware.com/articles/fog0000000069.html)：把旧代码全部扔掉，从零彻底重写。更离谱的是，他们在启动 Mozilla 项目时又把同样的错误重犯了一遍，造出了一个彻底失控的庞然大物，光是为了熬到 Alpha 内测阶段就足足耗费了*好几年*光阴。

我个人的私房理论是：要想治好程序员不爱写文档的毛病，可以把他们送去上[高强度的英文写作集训课](http://www.yale.edu/engl450b/)，帮他们克服对文字写作的恐惧；另一个办法则是雇佣聪明绝顶的项目/产品经理（Program Managers），由他们专门负责撰写真正高质量的书面规格文档。无论走哪条路，你都应该在团队里严格执行一条最简单的铁律：**“没有设计文档，绝不写一行代码（No code without spec）。”**

如果你想系统了解如何撰写优秀的软件设计规格文档，请阅读我的《[无痛功能规格文档四部曲](https://www.joelonsoftware.com/articles/fog0000000036.html)》。

## 8. 程序员拥有安静无打扰的工作环境吗？

给知识工作者提供独立空间、安静环境与个人隐私所能带来的生产力暴涨，早已被无数实证研究反复证实。软件工程管理领域的殿堂级名著《[人件](http://www.amazon.com/exec/obidos/ASIN/0932633439/ref=nosim/joelonsoftware/)》（*Peopleware*）就用详尽的数据记录了这些惊人的生产力收益。

问题出在哪儿呢？我们都知道，知识工作者只有在进入**“心流（Flow）”**状态，也就是俗称的“进入状态（In the zone）”时，才能发挥出巅峰战斗力。在心流状态下，他们的注意力高度聚焦在手头的工作上，周围环境的干扰被彻底屏蔽，他们甚至会忘记时间的流逝，凭借绝对的专注创造出卓越的成果。作家、程序员、科学家乃至篮球运动员，都会告诉你“进入心流状态”时的奇妙体验，那也是他们产出全部高质量成果的黄金时刻。

麻烦在于，进入“心流状态”一点都不容易。如果你试着去测量就会发现，从坐下来开始工作到进入最高效的心流状态，平均需要预热整整 **15 分钟**。有时候如果你身体疲惫，或者当天已经消耗了大量脑力去做创造性工作，你甚至根本没法再进入心流状态，剩下的工作时间只能百无聊赖地东摸摸西看看，刷刷网页、玩玩俄罗斯方块混过去。

另一个更致命的麻烦是：**把一个人从心流状态里“拽出来”实在是太容易了。** 噪音、电话铃声、出门吃午饭、花 5 分钟开车去星巴克买咖啡，以及同事的打断（*尤其是*同事跑过来打断你），全都会瞬间击碎你的心流。假如一位同事跑过来问你一个问题，表面上看只打断了你 1 分钟，但这 1 分钟却把你从心流状态里彻底拽了出来，导致你接下来需要花整整半个小时才能重新找回高效状态，那你的整体生产力就已经遭到了毁灭性打击。如果你身处那种当年狂喝咖啡的互联网泡沫公司最爱搞的“敞开式大牛棚（Bullpen）”办公区里，程序员旁边就坐着扯着嗓子打电话咆哮的市场销售人员，那么知识工作者的生产力就会直线跳水，因为他们每隔几分钟就会被打断一次，一辈子也别想进入心流状态。

对于程序员来说，打断造成的伤害尤为惨重。写代码的生产力，高度依赖于你能否在大脑的**短期工作记忆**里同时抛接十几个错综复杂的微小细节。任何一丁点外部打断，都会让这座由细节搭起的纸牌屋瞬间轰然倒塌。等你回过神来继续写代码时，你脑子里的那些上下文细节（比如刚才正在用的局部变量名叫什么、那个搜索算法刚才写到哪一步分支了）已经忘得一干二净，你不得不重新翻代码把它们一个个找回来，在重新热机恢复全速之前，你的效率会被拖慢到令人发指的地步。

不妨让我们算一笔最简单的代数账。假设（正如大量实证研究所揭示的那样）每打断一名程序员 1 分钟，实际上就会直接炸毁他 **15 分钟**的有效生产力。现在，让我们把两名程序员杰夫（Jeff）和马特（Mutt）安排在标准“呆伯特漫画式肉牛催肥场”里紧挨着的两个开放式工位（Cubicles）上。马特突然想不起来 C 语言里 `strcpy` 函数的 Unicode 宽字符版本叫什么名字了。他可以自己查文档，那需要花 30 秒；或者他可以直接转过头问旁边的杰夫，那只需要花 15 秒。因为他就坐在杰夫正旁边，他自然顺嘴问了杰夫。结果杰夫被这一问直接打断了思路，白白损失了 15 分钟的生产力（仅仅为了帮马特省下 15 秒）！

现在，让我们把他们俩搬进两间有实体墙壁、能关上门的独立办公室里。这时候当马特又想不起那个函数名时，他自己查文档依然只需要 30 秒；但如果他想跑去问杰夫，现在就得花上 45 秒，而且还得从椅子上站起来走过去（考虑到程序员群体的平均体能状况，从椅子上站起来绝不是件轻松的差事！）。于是他干脆自己查了文档。结果呢？现在马特只花了 30 秒查资料，而我们为杰夫整整省下了 15 分钟的心流生产力！啊，多么美妙的算术！

## 9. 你们使用金钱能买到的最好工具吗？

用编译型语言写代码，大概是如今在普通家用电脑上依然没法“瞬间完成”的最后几件工作之一了。如果你的代码编译过程需要超过几秒钟，给程序员换上市面上最新、最顶配的电脑就能立竿见影地省下海量时间。只要编译时间长达哪怕 15 秒，程序员在等待编译器干活的空档就会觉得无聊，然后顺手切到浏览器去看讽刺新闻网《[洋葱报](http://www.theonion.com/)》（The Onion），结果一下子被吸进去，整整几个小时的生产力就这么泡汤了。

在单显示器系统上调试图形界面（GUI）代码，就算不是完全不可能，也绝对是一场折磨。如果你在写 GUI 或前端界面代码，配齐双显示器会让调试工作轻松太多。

绝大多数程序员迟早都得为软件图标或工具栏处理一下位图图片，但绝大多数程序员手头连一款趁手的位图编辑器都没有。试图用 Windows 自带的“画图（Microsoft Paint）”去修改图标位图简直是个笑话，可现实中偏偏有大把程序员每天都在受这种罪。

在[我的上一份工作](https://www.joelonsoftware.com/articles/TwoStories.html)里，公司的系统管理员成天用自动脚本给我发警告垃圾邮件，抱怨我在服务器上占用的硬盘空间居然超过了……你敢信吗……**220 MB**！我直接回信算了一笔账：按照现在的硬盘价格，220 MB 硬盘空间的成本，甚至还远远赶不上我在公司上厕所用的*卫生纸*的钱。让我哪怕花上 10 分钟去清理目录腾空间，都是对高薪研发生产力极其荒谬的浪费。

==**一流的研发团队绝不会折磨自己的程序员。**== 哪怕是因为使用性能拉胯的烂工具而产生的一丁点微小挫败感，日积月累下来也会让程序员变得暴躁易怒、心情沮丧。而一个心情暴躁的程序员，绝对是一个毫无产出的程序员。

更何况……程序员简直是全世界最容易被“收买”的群体：你只要给他们配齐最酷炫、最新潮的顶级软硬件装备，就能让他们干得心花怒放。比起在薪水市场上真刀真枪地砸高薪抢人，给他们买顶级工具简直是让他们死心塌地为你卖命的最廉价、最划算的投资！

## 10. 你们有专职的测试人员吗？

如果你们团队没有配备专职的测试人员（Testers），至少达到**每两到三名程序员配备一名专职测试**的比例，那么你们要么是在往外交付满是漏洞的残次品，要么就是在干一件极其败家的蠢事：让时薪 100 美元的程序员，去干时薪 30 美元的测试人员就能干好的活儿。在测试人员编制上抠门省钱，是软件行业里最令人发指的“假省钱真败家（False Economy）”，我简直无法理解为什么居然还有那么多管理者意识不到这一点。

不妨读一读我专门就这个话题写的文章《[你们没有专职测试人员的五大（荒谬）借口](https://www.joelonsoftware.com/articles/fog0000000067.html)》。

## 11. 新候选人在面试时会被要求现场写代码吗？

你会不让魔术师现场变几个魔术，就直接掏钱雇他上台表演吗？当然不会。

你会在尝都没尝过一口菜的情况下，就直接敲定自己婚礼酒席的餐饮承包商吗？我对此深表怀疑。（除非那位大厨是你的玛吉姨妈，而且要是你不让她端出那道“远近闻名”的招牌切碎猪肝蛋糕，她会记恨你*一辈子*。）

然而，在软件行业里，每天都有无数程序员仅仅因为简历看起来光鲜亮丽，或者因为面试官跟他们聊得挺投缘，就被草率地录用了。又或者，面试官会问他们一堆死记硬背的边角料八股文（比如“在 Windows API 里 `CreateDialog()` 和 `DialogBox()` 有什么区别？”），而这种问题在真实工作中明明翻一下文档 10 秒钟就能查到。你根本不关心他们脑子里是不是背熟了几千条编程冷知识，你真正关心的是他们**到底能不能亲手写出代码来**。更有甚者，有些面试官喜欢考那种令人作呕的“脑筋急转弯（AHA! questions）”：那种一旦你知道答案就觉得简单得要命，但要是你没听过答案、当场怎么想也绝对想不出来的怪题。

求求你们了，*快停下这种蠢行吧*。面试时你想怎么聊都行，但请务必让候选人**现场亲手写一段代码**。（想要了解更多面试实战技巧，请阅读我的《[软件研发面试游击队指南](https://www.joelonsoftware.com/articles/fog0000000073.html)》。）

## 12. 你们做走廊可用性测试（Hallway Usability Testing）吗？

什么叫**“走廊可用性测试”**？就是当你刚写完一段界面代码时，直接冲到办公室走廊上，随便逮住下一个路过的同事，按着他在电脑前试着操作你刚写出来的程序。==只要你对 **5 个人**做过走廊可用性测试，你就能发现代码中 **95%** 的交互可用性问题。==

优秀的用户界面（UI）设计并没有你想象的那么高不可攀，而如果你想让客户真正爱上并掏钱购买你的产品，良好的界面交互是生死攸关的。你可以免费阅读我写的在线小书《[程序员 UI 设计入门指南](https://www.joelonsoftware.com/uibook/chapters/fog0000000057.html)》。

但关于用户界面，最重要的一条铁律是：只要你肯把自己写的程序拿给寥寥几个人（事实上，五六个人就完全足够了）现场试用一下，你就会瞬间发现用户在操作时卡壳的最大痛点在哪里。不妨读一读可用性大师[雅各布·尼尔森（Jakob Nielsen）的文章](http://www.useit.com/alertbox/20000319.html)，里面科学地解释了为什么只需要 5 名测试用户就能揪出绝大部分问题。哪怕你本身缺乏专业的 UI 设计功底，只要你强迫自己养成做“走廊可用性测试”的习惯（这玩意儿一分钱成本都不用花），你做出来的软件界面就会好上千百倍。

## 使用“乔尔测试”的四种方式

1. **给你们自己的研发团队打个分**，顺便把分数告诉我，好让我攒点八卦谈资。
2. **如果你是研发团队的管理者**，请把这 12 条当作你的日常体检核对清单，确保你的团队始终运转在最佳状态。等哪天你们团队能稳稳拿到 12 分满分时，你就可以[彻底放手让程序员们安心写代码](https://www.joelonsoftware.com/articles/fog0000000072.html)，而你只需要全职干好一件事：像门神一样挡在门口，别让业务部门的人跑进去烦他们。
3. **如果你正在看工作机会、犹豫要不要接某个程序员 Offer**，不妨在面试反问环节直接拿这 12 道题去考考你的未来雇主，看看他们能得几分。如果分数太低，请务必确认你入职后拥有推动整改这些乱象的实权；否则你进去之后一定会活在无尽的挫败与低效内耗之中。
4. **如果你是一名正在做技术尽职调查（Due Diligence）的投资人**，想要快速评估一支研发团队的真实成色，又或者你的软件公司正在考虑并购另一家公司，这份“乔尔测试”能为你提供一把快准狠的黄金标尺。
