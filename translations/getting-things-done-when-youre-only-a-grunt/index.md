# 只是个普通小兵，怎么把事做成

> 原文：[Getting Things Done When You’re Only a Grunt](https://www.joelonsoftware.com/2001/12/25/getting-things-done-when-youre-only-a-grunt/) · 作者：Joel Spolsky · 发布时间：2001 年 12 月 25 日

![只是个普通小兵，怎么把事做成](/images/getting-things-done-when-youre-only-a-grunt/cover.webp)

这个网站平时聊的都是软件管理。但很多时候，你在公司里并没有靠一纸行政命令推动变革的权力。如果你只是排在食物链底端的普通一线程序员，显然没法直接下令让大家开始做排期表、建缺陷库。其实就算你是管理者，大概也早就发现，管程序员跟放猫差不多，还没放猫有趣。光靠嘴上说一句“就这么办”，事情并不会自动办成。

待在一家[乔尔测试](/translations/joel-test/)得分很低的公司里，确实让人憋屈。不管你自己的代码写得多好，同事写出来的烂代码照样让你羞于承认自己参与过这个项目；或者管理层在“该写什么代码”这件事上频频拍错板，逼着你把大好才华浪费在给儿童退休规划小游戏调试 AS/400 版本上。

当然，你也可以直接辞职走人。但通常你留在这里总有不得已的理由：股票期权还没归属、这座小城里找不到更好的下家，或者老板正扣着你心爱的人当人质。不管什么原因，在烂团队里过日子确实气人。不过，自下而上改善团队还是有办法的，下面分享几条实用策略。

## 策略一：先自己动手干

很多改善项目的事，一个人就能先做起来。团队没有每日自动构建服务器？自己搭一台，在自己机器上配个定时任务，每天夜里自动跑构建并把结果发邮件出来。构建步骤太繁琐？自己把构建脚本写好。没人做可用性测试？拿张草图或简易原型，顺路拉收发室的同事做几分钟“走廊测试”就行。

## 策略二：借用口碑传播的力量

[乔尔测试](/translations/joel-test/)里的许多做法，哪怕整个团队都不配合，也能先由一个人落地。其中不少事，只要你做得够好，自然会慢慢传遍整个团队。

举个例子，假设团队里谁也劝不动去用[缺陷跟踪库](/translations/painless-bug-tracking/)。别为此心烦，你自己先维护一份。把自己代码里发现的 Bug 录进去；如果发现一个本来该由别人修的 Bug，就在系统里指派给对方。只要选一款顺手的缺陷跟踪软件（比如 [FogBUGZ](http://www.fogcreek.com/FogBUGZ)），系统会自动给对方发提醒邮件，要是他不修，你还能继续催。用着用着，大家就会体会到缺陷跟踪的好处，开始按规矩用起来。如果测试团队拒绝往系统里提 Bug，那你就干脆拒绝通过其他任何渠道接 Bug。大概说到第三千遍“听着，我很想帮你修，但我转身就会忘，麻烦录进系统里好吗”的时候，他们就会乖乖用起来了。

团队里没人愿意用版本控制？那就先在自己硬盘上建个 CVS 仓库。哪怕没人配合，你也可以先把自己的代码独立管理起来。等哪天同事碰上只有版本控制能救命的麻烦（比如手滑把 `rm *~` 敲成了 `rm * ~`），他们自然会跑来找你救急。慢慢地，大家就会意识到自己也可以拉一份代码来用。

## 策略三：先建起一块“优秀飞地”

团队不做[排期表](https://www.joelonsoftware.com/articles/fog0000000245.html)？不写[规格说明](https://www.joelonsoftware.com/articles/fog0000000036.html)？你自己写。你要是花一两天时间，把自己接下来要做的活写一份精简的规格说明和排期表，没人会拦着你。

想办法往团队里招更优秀的人。主动参与招聘和[面试](https://www.joelonsoftware.com/articles/fog0000000073.html)，把靠谱的候选人拉进队里。

在团队里找出那些愿意进步、也有能力进步的人，把他们拉到你这边。就算是很差的团队，通常也会有几个脑子聪明、只是缺经验写出好代码的人。帮他们一把，帮他们搭好成长环境，看看他们提交的代码。如果他们写出了蠢代码，千万别发一封居高临下的邮件教训对方“你这段代码蠢在哪”，那样只会激怒对方、竖起防备。相反，你可以装作无意间发现，提一个由那次提交引发的 Bug，让他们自己去查原因。亲手揪出来的 Bug，教训记得牢得多。

## 策略四：把“猪队友”隔离起来

哪怕是最好的团队，偶尔也会混进一两个不靠谱的人。团队里有糟糕的程序员，最让人头疼的地方在于：他们的烂代码会把你的好代码弄崩，或者逼得优秀程序员整天替他们擦屁股。

作为一线小兵，你的目标是把破坏降到最低，也就是“隔离控制”。迟早有一天，这些“天才”会花两周时间写出一段烂到离谱、根本不可能正常运转的代码。你心里肯定痒痒，恨不得花十五分钟自己从头重写一遍。忍住这个冲动。你手里正握着一个绝佳机会，能把这个麻烦精稳稳牵制住好几个月：不停往他那段代码上提 Bug 就行。他别无选择，只能埋头苦改上好几个月，直到你再也找不出新 Bug 为止。在这几个月里，他也就腾不出手去祸害别处的代码了。

## 策略五：躲开打扰

幸福的工作环境都是相似的：独立办公室、安静的氛围、好用的工具、极少的打扰，以及更少的大型会议。不幸的工作环境则各有各的不幸。

坏消息是，在几乎任何公司里，想改变整体办公环境都难如登天。签了长期租约之后，有时候连 CEO 都无能为力。这也是为什么拥有独立办公室的程序员少之又少。这对公司至少有两重伤害：第一，更难招到顶尖开发者，条件相同时大家肯定选环境更舒服的公司；第二，频繁打扰会大幅拉低开发效率，程序员根本没法进入专注状态，更别提长时间保持。

你得自己想办法跳出这种环境。拎着笔记本去公司食堂，那里白天大部分时间都空着一堆桌子，而且没人找得到你。或者把一间会议室订上一整天，躲在里面写代码，然后用密集的代码提交记录清清楚楚地展示：一个人待在安静房间里，你的产出到底高出多少。下次项目赶工、经理跑来问你“明天前交付需要什么支持”时，你就知道该怎么提要求了。他们会立刻给你腾出一间办公室用一天；用不了多久，他们自己就会开始琢磨，怎么才能让你全年都保持这种高效状态。

也可以错峰上班，晚来晚走，等全公司下班后的那几个小时往往效率最高。反过来，如果你所在的开发团队普遍爱晚来，那就早上九点到岗。在别人陆续过来打扰你之前的这两小时里，你能干完的活，比这一天剩下的时间加起来都多。

还有，千万别让邮件客户端或即时通讯软件一直挂着。如果你想看，每小时集中查一次就行，但别让它常驻前台。

## 策略六：让自己变得不可替代

==如果你自己不是一名真正出色的贡献者，上面所有策略都会失效==。如果你写不出好代码、产出又不够多，你在那儿折腾缺陷库只会招人反感，大家会觉得你不务正业。对职业生涯最致命的标签，莫过于被人觉得“整天操心流程，自己却干不出什么实事”。

有一次我跳槽去一家新公司当普通程序员，进去一看，这家公司在[乔尔测试](/translations/joel-test/)上大概只能拿 2 分，我下定决心要改变局面。但我也清楚，留下靠谱的第一印象至关重要。于是我把每天的前七个小时全部用来专心写代码，把本职工作做到位。没有什么比一连串扎实的代码提交，更能让你在研发团队里赢得尊重的了。同时，我每天下班前会留出一个小时来改善流程：修掉那些让产品极难调试的顽疾，搭起每日构建和缺陷库，清理掉长期困扰开发的破事，给白天写的功能补上规格说明，写了一份手把手教人从零搭开发环境的文档，还把公司内部一门一直没文档的重要语言彻底补全了文档。慢慢地，整个流程越来越顺。后来除了我自己（以及后来交给我带的团队），别人依然不怎么写排期和规格说明，但除此之外，我们在乔尔测试上的得分一路涨到了 10 分左右。

哪怕手里没有职权，你照样可以让局面变好，前提是你必须像“凯撒的妻子”一样无懈可击。否则，你一路走来只会四处树敌。

> **[译者注：文中的几个年代细节与典故]**
>
> - **CVS 与 `rm * ~`**：CVS 是 Git 普及前常用的早期版本控制工具。命令 `rm *~` 本意是删除以 `~` 结尾的临时备份文件，一旦中间手滑多敲一个空格变成 `rm * ~`，就会把当前目录里的所有文件一口气删光。
> - **“凯撒的妻子（Caesar's Wife）”**：出自古罗马典故“凯撒的妻子必须不容怀疑（Caesar's wife must be above suspicion）”。乔尔借这个说法点出了全文最实在的前提：在没有职权时想推动团队改流程，自己先得把本职代码交得无可挑剔，每天“7 小时写代码 + 1 小时改流程”的分法，放到二十多年后的今天依然非常管用。
