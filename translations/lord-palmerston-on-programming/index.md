# 帕默斯顿勋爵论编程

> 原文：[Lord Palmerston on Programming](https://www.joelonsoftware.com/2002/12/11/lord-palmerston-on-programming/) · 作者：Joel Spolsky · 发布时间：2002 年 12 月 11 日

![帕默斯顿勋爵论编程](/images/lord-palmerston-on-programming/cover.webp)

曾经有过那么一个年代，只要读完彼得·诺顿（Peter Norton）写的[那一本书](http://www.amazon.com/exec/obidos/tg/detail/-/067130948X)，你就真的掌握了 IBM-PC 编程的全部知识。过去二十年里，全世界的程序员一直在 IBM-PC 之上叠了一层又一层抽象，想让编程变得更容易、更强大。

但根据[抽象漏洞法则](/translations/leaky-abstractions/)，尽管这些抽象原本是为了简化编程，想要成为一名优秀程序员所必须掌握的知识总量，实际上却一直在膨胀。

哪怕只在一个编程世界里做到精通，真正的精通，都需要好几年时间。当然，很多聪明的少年这周学 Delphi，下周学 Python，再下周学 Perl，觉得自己样样精通。可他们压根不知道自己漏掉了多少东西。

我从 ASP 和 VBScript 一发布就开始用它们。VBScript 算是地球上最迷你的语言，ASP 编程满打满算也就 5 个类，常用的还只有两个。可直到现在，我才觉得自己终于摸清了如何合理设计一个 ASP/VBScript 应用的架构：数据库访问代码放在哪儿最合适、怎么用 ADO 取记录集、怎么把 HTML 和逻辑代码拆干净等等。我也终于改用正则表达式，不再到处写一次性的字符串处理函数。就在上周，我才刚弄明白怎么把 COM 对象从内存里卸载掉，好在不重启整个 Web 服务器的前提下重新编译它。

Fog Creek 规模太小，养不起各路专才。所以当我需要为自家基于 ASP/VBScript 的产品 [FogBUGZ](http://www.fogcreek.com/FogBUGZ) 写一个真正好用的[安装程序](https://www.joelonsoftware.com/news/20021002.html)时，我动用了好几年积累的 C++/MFC 经验、多年的 Windows API 经验，甚至还用上了 Corel PhotoPaint 的手艺，好在安装向导的角落里画一张清爽的配图。后来为了让 FogBUGZ 完美支持 Unicode，我又得用 C++ 和 ATL 写一个小型 ActiveX 控件，这靠的是多年的 C++ 和 COM 功底，再加上之前做 CityDesk 时花了一周多啃下来的字符编码知识。

所以当我们碰上一个只在 Windows NT 4.0 上出现的诡异 Bug 时，我只花了 3 分钟就定位出来了：因为我会用 VMWare，手头正好配着一台干净的 NT 4.0 虚拟机，懂怎么用 Visual C++ 远程调试，还知道去查 EAX 寄存器看函数返回值。换个刚入门的新手，排查同一个问题可能得花上一个小时甚至更久。而我背后靠的，是从 1982 年买到第一台 IBM-PC 和那本诺顿的书开始，一路攒下来的海量杂学。

==抽象漏洞让我们面对一条“曲棍球棒”式的学习曲线：日常用到 90% 的内容，花一周就能学会；可剩下的那 10%，往往得花上好几年去补==。真正资深的程序员，拉开和那些张口就是“不管让我做什么，找本书学几天就行”的人的差距，就在这 10% 上。搭团队时，让一批经验尚浅的程序员拿着高层抽象工具大块大块地码业务代码没问题，但如果团队里没有几位真正经验老到的成员来啃最硬的骨头，整个团队是转不起来的。

软件行业里有很多彼此独立的“编程世界”，想在其中任何一个做到真正精通，都需要极其庞大的知识储备。下面是我个人最熟的三个：

- MFC / C++ / Windows
- VBScript / ASP
- Visual Basic

说白了，全都可以归为 Windows 编程。我也写过 Unix 和 Java 代码，但写得不多。我在 Windows 编程上的熟练度，靠的并不只是几门基础技术，而是背后整套支撑生态。我敢说自己很擅长 Windows 编程，是因为我还懂 COM、ATL、C++、80×86 汇编、Windows API、IDispatch（OLE 自动化）、HTML、DOM、IE 对象模型、Windows NT 与 Windows 95 底层机制、LAN Manager 和 NT 网络与安全机制（ACE、ACL 那一套）、SQL 与 SQL Server、Jet 与 Access、JavaScript、XML，外加一堆其他零零碎碎的常识。当 VB 里的 `StrConv` 函数干不了我想要的活时，我可以毫不费劲地顺手写个 COM 控件，钻进 C++ 和 ATL 里直接调用 MLang 接口。走到这一步，花了我好几年。

除此之外，还有许许多多别的编程世界。有人扎根在 BEA WebLogic 的世界里，精通 J2EE、Oracle 以及一整套我连名字都报不全的 Java 生态；也有硬核的 Macintosh 开发者，熟悉 CodeWarrior、MPW、从 System 6 到 OS X 的 Toolbox 编程、Cocoa、Carbon，甚至还懂 OpenDoc 这种如今已经派不上用场的昔日好东西。

但几乎没人能同时精通两三个以上的世界，因为要学的东西实在太多了。除非你在其中一个世界里扎扎实实干上两年以上，否则根本吃不透。

可偏偏你又必须去学。

不少人去面试时，因为没有 Win32（或者 J2EE、Mac 开发之类）的经验被拒，心里很不服气；或者接到糊涂猎头的电话，对方连 MSMQ 是什么都不知道，却张口就问“你有没有 5 年 MSMQ 经验”，听得人一肚子火。

在真正干过一阵 Windows 开发之前，你可能会觉得 Win32 不过是个普通库，和其他库没什么两样，买本书翻翻，用到的时候查着调就行了。你可能会以为，扎实的编程基本功（比如精湛的 C++ 功底）占 90%，各种平台 API 只不过是占 10% 的边角料，几周就能补上。对于抱有这种想法的人，我只能客气地提醒一句：时代变了，这个比例已经倒过来了。

如今很少有人还有机会整天写底层 C 算法去搬运字节了。我们大多数人现在[几乎把所有时间](https://www.joelonsoftware.com/articles/fog0000000250.html)都花在调用 API 上，而不是搬运字节。一个 C++ 功底极强却毫无平台 API 经验的程序员，在写基于某个平台的日常代码时，其实只掌握了大约 10% 的必备知识。经济[景气](https://www.joelonsoftware.com/articles/fog0000000050.html)的时候这无所谓，你照样能找到工作，雇主愿意替你承担熟悉平台的培训成本。可一旦经济[不景气](http://sfgate.com/cgi-bin/article.cgi?f=/c/a/2002/10/20/IN.DTL)，一个岗位涌来 600 份简历，雇主就有底气直接挑那些已经吃透目标平台的专家，比如随口就能说出用 Visual Basic 做 FTP 传文件的四种办法并讲清各自利弊的人。

这些编程世界各自庞大的知识面，也催生了网上无数毫无意义的口水战，大家整天争论谁的世界更高级。下面是我论坛里某位匿名网友留下的一句得意洋洋的评论：

> “又多了一个让我庆幸活在‘自由世界’的理由。近乎绝对的言论自由，而且不用去伺候安装程序和注册表这类东西，这还只是冰山一角。”

我猜这位朋友想说的是，Linux 世界里不用写安装程序。很抱歉扫你的兴，你们那边有同样复杂的东西：`imake`、`make`、各种配置文件一大堆；折腾完了，发布软件时还得附带一个 20KB 的 `INSTALL` 文件，里面写满自作聪明的提示，比如“你需要先装 zlib”（*那是什么？*）或者“这步可能要花点时间，去吃点 Runts 糖吧”。至于注册表，你们确实没有一个统一规整的键值对总库，取而代之的是上千种各自为政的文件格式，每个软件一套，`.whateverrc` 和 `foo.conf` 撒得满硬盘都是。想改 Emacs 的配置得先学写 Lisp，想改不同 Shell 的配置得分别学各自的脚本方言，没完没了。

只熟悉一个世界的人很容易沾沾自喜，每次听说另一个世界里有多麻烦，就以为自己的世界清清爽爽。其实麻烦一样不少，只不过你已经足够熟练，早就跨过去了。如今这些技术世界实在太庞大、太复杂，根本没法拿来简单比较。正如英国首相帕默斯顿勋爵的名言：“石勒苏益格-荷尔斯泰因问题复杂到整个欧洲只有三个人真正懂过：第一位是阿尔伯特亲王，他已经去世了；第二位是一位德国教授，他疯了；第三位就是我，但我已经忘得一干二净。”软件世界同样庞大、复杂、盘根错节。每当我看到本来挺聪明的人在博客里写下“微软就是做不好操作系统”这种[空洞论断](http://www.winterspeak.com/2002_10_01_archive.html#85572348)时，坦白说，他们看起来真挺蠢的。试想一下，面对成千上万名程序员花一二十年写出来的几百万行代码、几百个核心功能模块，连任何单个个体都摸不透其中一小半，却试图用一句话盖棺定论。我并不是在替微软辩护，我只是想说，站在极度无知的位置上大而化之地指点江山，是今天互联网上最浪费时间的事之一。

常看我博客的读者大概已经注意到，我最近一直在琢磨怎么在不为 Linux 和 Macintosh 版本付出不成比例成本的前提下，把应用同时交付到 Linux、Mac 和 Windows 上。要做到这一点，你需要某种跨平台开发库。

Java 试过这条路，但 Sun 公司对图形界面（GUI）的理解不够深，做不出真正顺滑、有原生质感的应用。就像《星际迷航》里透过望远镜观察地球的[外星人](http://www.voyager.cz/tos/epizody/19squireofgothostrans.htm)，他们精准复制了人类食物*看起来*该是什么样，却没意识到食物还得*吃起来*有味道。Java 应用的菜单栏摆在正确的位置上，但各种键盘快捷键的行为和其他 Windows 软件全不一样，带标签页的对话框也看着有点渗人。无论你怎么折腾，都别想让它的菜单栏做得和 Excel 一模一样。为什么？因为每当抽象层出现漏洞时，Java 压根没给你留一条顺畅的路钻回原生底层。用 AWT 写界面时，你拿不到窗口的 `HWND`，调不了微软的原生 API，更别提拦截 `WM_PAINT` 自己重绘了。而且 Sun 态度非常明确：你要是敢这么干，你就不“纯粹”了，你被“污染”了，滚一边去吧。

在经历了几起人尽皆知的 Java 桌面应用败局（比如 Corel 的 Java 版 Office 套件和 Netscape 的 Javagator）之后，已经有足够多人明白该远离这片泥潭。[Eclipse](http://www.eclipse.org/) 干脆基于原生控件从零造了[一套自己的窗口库](http://www.eclipse.org/articles/Article-SWT-Design-1/SWT-Design-1.html)（SWT），只为了让 Java 写出来的界面能有一点像样的原生观感。

Mozilla 工程师决定另起炉灶，发明了一套叫 XUL 的方案来解决跨平台问题。到目前为止，效果挺让我惊喜，Mozilla 终于做到了“吃起来像真食物”。连我最较真的一个细节，按 `Alt+Space` 再按 `N` 最小化窗口，在 Mozilla 里都能正常生效。虽然花了不少时间，但他们真做出来了。

创办了 Lotus 并打造出 Lotus 1-2-3 的米奇·卡普尔（Mitch Kapor），[决定](http://blogs.osafoundation.org/mitch/000007.html)在他的下一个项目里用 wxWindows 和 wxPython 来做跨平台支持。

那么 XUL、Eclipse 的 SWT 和 wxWindows，到底哪个更好？我不知道。它们各自都是极其庞大的世界，我没法随便评判。光看教程远远不够，你必须跟着它流汗流血熬上一两年，才能真正确认它到底够不够好，或者无奈发现无论怎么折腾都做不出真正的原生手感。偏偏大多数项目在写第一行代码之前，就得决定押注哪个世界，而那恰恰是你信息最少的时候。我以前待过一家公司，不得不长期忍受一套极其糟糕的架构，就因为最早那批程序员拿这个项目一边自学 C++、一边自学 Windows 编程。最早的一批代码写出来时，作者压根没搞懂事件驱动编程是怎么回事；核心字符串类（我们当然自己造了个字符串类）简直是“设计 C++ 类时能犯的所有错误”的教科书级合集。后来我们花大力气清理重构了不少老代码，但它还是困扰了我们很久。

==所以眼下我的建议是：如果团队里连一位在目标语言、类库、API 和平台上攒了几年扎实经验的架构师都没有，就别贸然开新项目==。如果平台有的选，优先用团队功底最深的那一个，哪怕它不是最时髦的，或者纸面上不是效率最高的。而当你自己负责设计抽象层或开发工具时，多花点心思，尽量把它做得少些漏洞。

> **[译者注：关于帕默斯顿勋爵，以及二十多年后的今天]**
>
> **帕默斯顿勋爵（Lord Palmerston）** 是 19 世纪两度出任英国首相的政治家。文中他调侃的“石勒苏益格-荷尔斯泰因问题”，是当时牵涉丹麦、普鲁士和德意志邦联的公国继承与归属纠纷，条约和历史纠葛极其复杂，后来在英语里常被借用来形容“复杂到没人能完全理清的烂摊子”。
>
> 这篇文章写于 2002 年，文里的 ASP、COM、AWT、XUL 如今大多成了历史名词，但把它们换成今天的 React、Next.js、Kubernetes、Flutter 或微信小程序，会发现乔尔说的那条“曲棍球棒学习曲线”几乎一点没变：一周能跑通 Demo，真遇到线上诡异的渲染、内存或权限问题，靠的还是在某个生态里踩过几年坑攒下来的直觉。文中开篇提到的[《抽象漏洞法则》](/translations/leaky-abstractions/)本站也已收录，可以对照着看。
