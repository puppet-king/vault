# 无痛缺陷跟踪指南（Painless Bug Tracking）

> **原文标题：** [Painless Bug Tracking](https://www.joelonsoftware.com/2000/11/08/painless-bug-tracking/)  
> **原文作者：** Joel Spolsky（2000 年 11 月 8 日） · [查看英文原版](./en.md)

---

![无痛缺陷跟踪手绘全览](/images/painless-bug-tracking/painless-bug-tracking.webp)

当年老式电脑 TRS-80 的 Level-I BASIC 语言里，统共只能存下两个字符串变量 `A$` 和 `B$`。巧得很，我打娘胎里带出来的脑容量也一样：大脑里只有两个专门装 Bug 的插槽。不管在任何时候，我脑子里最多同时只能记住两个 Bug。要是你硬塞给我第三个，其中准有一个会咕噜一声掉到地上，被扫进床底下喂给灰尘兔子吃掉。

老老实实维护一份缺陷数据库，正是[优秀的软件团队的标志之一](/translations/joel-test/)。可至今让我百思不得其解的是，真正在这么做的团队居然这么少。程序员群体里流传最广的一个离谱执念，就是坚信自己靠脑子就能记住所有 Bug，或者靠几张贴在显示器边框上的便利贴就够了。

如果你愿意借我几分钟听我唠叨，我想顺着之前那两篇《[无痛软件排期](https://www.joelonsoftware.com/articles/fog0000000245.html)》和《[无痛功能设计文档](https://www.joelonsoftware.com/articles/fog0000000036.html)》的路子，聊聊一套极其省心、毫不折腾的缺陷跟踪法。

首先，你得有一座正经的数据库。如果只是两个哥们儿趁着三天小长假凑一块儿写点小脚本，拿个纯文本文件充当 Bug 库倒也勉强凑合。只要规模比这大出哪怕一丁点，你就必须用上正经的缺陷跟踪系统。市面上一抓一大把现成的系统可以买（顺便毫无掩饰地打个硬广：我们 Fog Creek Software 自己动手开发的缺陷跟踪工具 [FogBugz](http://www.fogcreek.com/FogBugz/)，基于网页运行，用起来顺手得不得了，功能也相当硬核，就算我自卖自夸也是实话）。

为了讲透这里面的门道，咱们不妨全程盯紧一条真实的 Bug，看它从刚刚破壳诞生的那一刻起，一路流转到最后被人彻底解决安乐死为止。咱们追踪的正是那条大名鼎鼎的 **1203 号 Bug**。缺陷库里关于这条 Bug 的档案长下面这样：

| 字段 | 内容 |
| :--- | :--- |
| **编号 (ID)** | 1203 |
| **项目 (Project)** | Bee Flogger 2.0 |
| **模块 (Area)** | FTP 客户端 |
| **标题 (Title)** | **上传文件会导致 FTP 服务端发生核心转储崩溃（dump core）** |
| **当前指派人 (Assigned To)** | 已关闭（CLOSED） |
| **状态 (Status)** | 已关闭（已解决：已修复） |
| **优先级 (Priority)** | 2 级：必须修复 |
| **目标修复版本 (Fix For)** | 2.0 Alpha |
| **发现版本 (Version)** | Build 2019 |
| **测试环境 (Computer)** | 吉尔（Jill）的 iMac，Mac OS 9.0，128M 内存，1024×768 千万色 |

**详细描述与流转记录：**

- **2000/11/1 · 由“极其极其优秀的测试员吉尔”创建（Opened）**
  - 启动 Bee Flogger
  - 新建一个未命名文档，只在里面敲入一个字母 `a`
  - 点击工具栏上的 FTP 按钮
  - 尝试用 FTP 上传到你的测试服务器
  - **Bug 现象：** 服务器彻底没响应了。跑一下 `ps -augx` 一查，FTP 进程压根不在运行列表中，而且根目录下赫然躺着一个 `core dump` 崩溃转储文件。
  - **预期结果：** 不应崩溃。
- **2000/11/1 · 吉尔将其指派给“主程威利”（Willie）**
- **2000/11/2（昨天）· 主程威利将其标记为“已解决：不予修复（WON'T FIX）”**
  - *“吉尔，这真不是咱们的代码出的锅，那只是 Linux 系统自带的 proftpd 服务端。”*
- **2000/11/2（昨天）· 吉尔重新激活（Reactivated）并再次指派给主程威利**
  - *“这话说不通。我平时用普通正常的 FTP 客户端连它从来没崩过。偏偏只要一用咱们的客户端去连，次次必崩。FTP 服务器可不会无缘无故自己崩溃玩。”*
- **2000/11/3（今天）· 主程威利将其转派给“程序员迈基”（Mikey）**
  - *“迈基，你过来瞅一眼？兴许是你那块客户端代码搞了什么幺蛾子。”*
- **2000/11/3（今天）· 程序员迈基将其标记为“已解决：已修复（FIXED）”**
  - *“我猜大概是我刚不小心把用户名当成密码传过去了之类的……”*
- **2000/11/3（今天）· 吉尔在 Build 2021 上复测失败，重新激活并退回给迈基**
  - *“在 Build 2021 里照样一跑就崩。”*
- **2000/11/3（今天）· 程序员迈基更新记录**
  - *“咦，这就怪了。让我单步调试深挖一下。”*
- **2000/11/3（今天）· 程序员迈基更新记录**
  - *“我现在怀疑罪魁祸首可能是那个自己写的 `MikeyStrCpy()` 函数……”*
- **2000/11/3（今天）· 程序员迈基再次标记为“已解决：已修复（FIXED）”**
  - *“啊哈！这回真修好了！”*
- **2000/11/3（今天）· 由[极其极其优秀的测试员吉尔](http://jemcfarlane.editthispage.com/)最终关闭（Closed）**
  - *“在 Build 2022 里验证确实修好了，那我就把这条单子正式关掉了。”*

幕后到底发生了什么事？过程是这样的。

程序员迈基正在 Macintosh 软件上欢快地猛敲新的 FTP 客户端功能。敲着敲着，这哥们儿一时手痒飘了起来，非要自己从零手写一个字符串拷贝函数。哼，让那帮整天唠叨“代码复用”的烦人精一边凉快去吧！哈哈哈哈！

迈基啊迈基，不肯乖乖复用现成轮子迟早是要遭报应的。今天这记现世报就是：迈基忘了在拷贝完的字符串末尾补上 `\0` 空字符结束符。可偏偏他在自己开发机上测试时一直没撞出来，因为绝大多数时候他碰巧把字符串拷进了一块预先清零初始化过的内存里。

那周晚些时候，极其极其优秀的测试员吉尔正在卖力虐待软件，拿脑门在键盘上左右疯狂翻滚，或者干着类似等级的魔鬼测试（顺便一提，世上大多数顶级测试员都叫吉尔，或者吉利安之类的变体名字）。突然间，极其诡异的事情发生了：她正在对接测试的 FTP 服务端守护进程**彻底崩掉了**！没错，我知道那是一台 Linux 服务器，Linux 机器号称永远不会崩溃（请 Slashdot 技术社区的各位大佬先别冷哼），但这鬼玩意儿今天就是实打实**崩了**。而且吉尔全程压根没动过服务器半根汗毛，她只不过是在 Mac 上用迈基写的新客户端往外传了几个文件而已。

现在轮到专业选手上场了。既然吉尔是位极其极其优秀的测试员，她平时一直一丝不苟地记着详尽的操作日志（比方说刚才拿脑门压键盘时精确的俯仰角和偏航角都白纸黑字记在实验本上）。于是她立刻把整台测试机彻底重启，从干干净净的初始环境重头再来一遍，照着步骤一复现，好家伙！Linux 的 FTP 服务进程**又崩了一回**！单单今天一天就已经崩了足足两回！这下总算没脾气了吧，林纳斯。

吉尔眯起眼睛审视手里那张复现清单。清单上足足列了大约 20 个操作步骤，其中好多步看着明显跟崩溃八竿子打不着。稍微折腾排查了一小会儿，吉尔就把整个复现流程硬生生压缩裁剪成了仅仅四步，而且每次走完这四步都百分之百精准引爆同款崩溃。好了，现在万事俱备，她可以正式提交 Bug 单了。

吉尔把这条新 Bug 录进了缺陷跟踪数据库。注意，单单“录入一条 Bug”这件事本身就需要守规矩：世上既有顶好用的 Bug 报告，也有一塌糊涂的垃圾 Bug 报告。

## 一份好 Bug 报告必备的三要素

> 于是主开口晓谕道：“汝当先拔出圣销。随后，汝须数到三，不多一分，不少一毫。三乃汝当计之数，且计数之终数亦必为三。四不可数，二亦不可数，唯数二以进三者除外。五则断然出局。及至第三之数即三既达，便当朝向汝敌猛掷手中之安提阿圣手雷；彼在我眼中既属顽劣之徒，定当一命呜呼。”
>
> 出自《巨蟒与圣杯》（*Monty Python and the Holy Grail*）

==一条好 Bug 报告的规矩好记极了：每份合格的报告必须且仅包含下面三样东西：==

- **复现步骤**（Steps to reproduce）、**你原本预期看到什么**（Expected），以及**你实际看到了什么**（Observed）。

听上去挺简单吧？真干起来可未必。作为一名程序员，平时老有人给我派发缺胳膊少腿的 Bug 单。

如果你不告诉我怎么复现这个 Bug，我多半压根听不懂你在念叨啥。“程序崩了，还在桌面上拉了一坨臭烘烘的不明物体。”听着挺热闹，亲爱的，可你不告诉我**你崩溃前到底在软件里点啥了**，我真是两眼一抹黑无从下手。当然我承认，世上确实有两类实在很难搞到精确复现步骤的情况。第一种是你实在记不清刚才点过啥了，或者只是在转述“一线外场（the field）”报上来的客诉。（顺便问一句，为啥英语要把用户现场叫“the field”？难不成用户全都站在麦田地里用电脑吗？算了不管了。）另一种可以勉强豁免的情况，是那个 Bug 属于“偶尔抽风出现、并非次次必现”，可即便这样，你依然应当附上复现步骤，顺手备注一句“目前不是每次必现，概率较低”。遇上这种间歇性幽灵 Bug，查起来肯定非常折磨人，但起码咱们顺着线索还能试着揪一揪。

如果你不写明**原本预期该是什么样**，我可能根本看不出这哪儿算 Bug 了。比如启动欢迎页上溅了一滩血。那又咋了？兴许是我通宵写代码时划破手指滴上去的呢，你原本到底指望它长啥样？哦，你翻出需求规格书说“产品要求启动页绝对不能带血”！行，这下我算完全明白你为啥管这叫 Bug 了。

第三部分是**你实际看到了什么结果**。连最后出了什么洋相都不肯告诉我，我就更不可能知道 Bug 到底在哪儿了，这一点实在不言自明。

## 回到咱们的小故事

闲话少叙，书归正传。吉尔把这条 1203 号 Bug 正式录进了系统。在一套设计合理的缺陷跟踪系统里，新提交的 Bug 会自动指派给该项目的主力负责人（Lead Developer）。这里藏着整套流程的第二个核心铁律：==每一条 Bug 在最终关闭之前，任何时刻都必须且只能指派给“唯一一个人”负责。== Bug 就像一块滚烫的烤山芋：只要它此刻挂在你名下，你就扛着全责去搞定它（不管是自己修好，还是查清归属后正式转派给真正该修的那位）。

主程威利点开这条 Bug，扫了两眼就断定这多半是人家 FTP 服务端自己的毛病，于是手起刀落把状态改成了“已解决：不予修复（Won't fix）”。毕竟这 FTP 服务器又不是咱们团队写的嘛。

一旦某条 Bug 被研发标记为“已解决”，系统就会立刻把它自动退回指派给当初提出这条 Bug 的人。这一点极其关键，千万不能弄反！Bug 绝不会仅仅因为某位程序员单方面觉得“这算完了”就从人间蒸发。==缺陷管理里最高等级的黄金铁律是：唯有当初打开（Open）这条 Bug 的发起人，才有权最后关闭（Close）这条 Bug。== 程序员只能把状态标记成“已解决（Resolved）”，意思是“嘿，我觉着我这边搞定了”；可要想真把这条 Bug 从台账里彻底“关闭（Closed）”勾销，必须由最初建单的人亲手复测确认真修好了，或者心服口服认可确实不该修才行。

吉尔很快收到一封邮件通知：山芋又飞回她自己手上了。她点开单子，读完主程威利留下的甩锅回复，心里觉得很不对劲。大伙儿用这套 FTP 服务好几年了向来稳如泰山，偏偏只要一用迈基写的新客户端去连，每次百分百崩。于是吉尔二话不说把这条 Bug 重新**激活（Reactivated）**，冷静写明自己的反驳理由，山芋原路退回给威利。这回威利总算不敢敷衍了，把它正式转派给了程序员迈基去排查。

迈基捧着单子苦思冥想了半天，结果彻底把病因诊断错了方向。他兴冲冲修好了一处跟这事八杆子打不着的另外什么 Bug，然后美滋滋地把吉尔这条单子标成了“已解决：已修复（RESOLVED - FIXED）”。

单子再次飞回吉尔面前。吉尔拿最新打出来的包照着那四步一通点，只听“砰”的一声，Linux 服务端再次光荣当场去世。吉尔面无表情地**再次激活**这条 Bug，二话不说直接退回给迈基。

迈基这下彻底懵了，只好硬着头皮从头单步顺藤摸瓜，最终终于抓到了那个该死的真实病根。（各位读者看到这儿猜出到底是哪儿出毛病了吗？我就留作思考题不直接揭底了，前文给的线索早就够破案啦！）迈基动手修净毛病、自测通过，果不其然！那组复现步骤这回终于不再把 FTP 服务器撞崩了。迈基再一次点下“已修复”。吉尔拿最新 Build 2022 复现了一遍，确认稳稳当当彻底正常，于是爽快点击“关闭”，为 1203 号 Bug 画上句号。

## 高效缺陷跟踪的十条核心秘诀

1. 一位优秀的测试员，总是会先花工夫把复现步骤尽量压缩成**最精简的几步**；这能帮后面接手查错的程序员省下海量排障时间。
2. 时刻牢记那条铁律：唯一有权**关闭（Close）**一条 Bug 的人，永远是当初提交它的发起人。团队里任何人都可以把它标记为**已解决（Resolve）**，但唯有当年亲眼目睹过惨状的那个人，才能最终确认眼前这个 Bug 是真的消失了。
3. 解决一条 Bug 往往有好几种收口方式。在 FogBugz 里，你可以选择将其标记为：*已修复（Fixed）*、*不予修复（Won't fix）*、*延期处理（Postponed）*、*无法复现（Not repro）*、*重复单（Duplicate）*，或者 *按设计本应如此（By design）*。
4. 所谓 *无法复现（Not Repro）*，意思就是团队里压根没人能重现出单子上描述的毛病。每当测试提上来的报告里缺了复现步骤，程序员常常就会甩出这个状态来退回。
5. 你们必须清清楚楚地追踪好每一个构建版本号。凡是发给测试人员验收的每一个安装包，都必须附带一个明确的构建号（Build ID）。免得可怜的测试人员拿错老版本，对着一个本就不该包含该修复的旧包白白把 Bug 复测一遍、然后怨声载道退回来。
6. 如果你是程序员，偏偏碰上测试团队怎么都不肯用缺陷数据库，招数极简单：**死活拒收一切通过其他渠道发来的报错。** 如果测试同学以前习惯给你直接发邮件提 Bug，直接把邮件原封不动退回去，只附一句简短回复：“请把这条录进 Bug 库里，实在抱歉，靠翻邮件我真记不住。”
7. 反过来，如果你是测试员，碰上油盐不进死活不用缺陷库的程序员，招数也一样极简单：**嘴上干脆别跟他们当面汇报 Bug**，安安静静全敲进系统里，让缺陷数据库自己给他们狂发邮件提醒就行了。
8. 如果你是程序员，团队里只有一半同事乖乖用 Bug 库、另一半人还在散兵游勇瞎沟通，那就直接开始在系统里把对应 Bug 往那几个同事名下指派。用不了多久，他们自己就会懂该怎么配合了。
9. 如果你是技术管理者，花了大价钱采购搭建好缺陷管理系统，底下却压根没人肯打开用，那就开始把**所有新功能开发任务也一律当成条目在库里指派下去**。一个好的缺陷跟踪库，顺带着本来就是一张极其好用的“待开发需求清单”。
10. ==最后一条千万忍住：死死克制住往 Bug 录入界面里疯狂新增字段的诱惑。== 大约每隔一两个月，团队里准会冒出一位聪明人，两眼放光提议往系统里再加一个绝妙新字段。你会听到各式各样貌似极其精明的主意，比如：必须强制记录是在哪个源码文件里爆的错、记录这个 Bug 大约按百分之多少的概率能复现、统计此前一共累计发生过多少次、或者精确抄录出事那台机器里每一个动态链接库 DLL 的具体版本号。千万、千万不能向这些念头妥协！只要你敢松一次口，要不了多久你们的新建 Bug 页面就会膨胀出整整一千个必填下拉框，最后结果就是整个团队谁都不想再往里提 Bug 了。缺陷库要想真正发挥威力，核心前提是全员人人愿意用；一旦走正经系统提一条 Bug 变得跟写论文一样麻烦，大家立刻就会本能地绕开缺陷库各自私下找捷径去。

哪怕整个团队里只有你一个人在孤军奋战写代码，只要你手里没有一份组织井然、记录着全部已知缺陷的清单，你最终交付出去的就注定只能是低质量代码。而在真正顶级的软件工程团队里，缺陷库不仅是全员每天的必用工具，大伙儿甚至会习惯拿它当成自己的私人“待办任务清单”，把浏览器的默认首页直接设成“当前指派给我的未解决 Bug 列表”，甚至忍不住偷偷幻想：要是有朝一日还能在系统里顺手建一条单子指派给行政大管家，让他赶紧补一箱山露（Mountain Dew）汽水进冰箱，那日子该有多美滋滋啊。

> **[本土化注：从“群聊截图甩锅”到 Jira / 飞书项目里的真实 Bug 单]**
> 读这篇写于 2000 年的文章，最让人会心一笑的是：二十多年过去，软件工具从当年的 FogBugz 进化成了今天的 Jira、Linear、GitHub Issues、禅道和飞书项目，可无数研发团队依然天天在重演当年的老剧本：
>
> 1. **警惕“微信群 / 钉钉截图报错”黑洞**：今天国内团队比当年更危险的一点，是即时通讯软件太顺手了。测试或运营随手在项目大群里丢一张模糊报错截图，开发嘴里回一句“收到我看下”，两小时后群消息刷过去几百条，这条 Bug 就真掉进床底喂给灰尘兔子了。记住第 6、7 条的冷酷原则：不进系统不算数，不挂到唯一责任人名下不算开始处理，开发点“已解决”不等于事情完了（[乔尔测试](/translations/joel-test/)第 5 条更要求先把已知 Bug 修完再写新代码）。
> 2. **警惕“为了数据好看疯狂往系统里加必填项”**：今天不少中大型研发团队的痛点，往往走到了第 10 条的反面。管理层为了年底做“千行代码缺陷率、模块返工热力图、测试效能大盘”，在新建缺陷页面里硬塞了十几个必填归因字段、多级分类标签和影响范围说明。结果一线测试嫌建单比直接走过去拍研发肩膀麻烦十倍，于是私下里靠“微信打招呼口头改掉”绕开流程，最后留在报表里的反而全是虚假繁荣的失真数字。维持字段极简（复现步骤 + 预期 + 实测 + 唯一指派人 + Build ID），再用真实工时沉淀出[《循证排期法》](/translations/ebs/)，才是既不内耗又能做出好产品的工程正道。
