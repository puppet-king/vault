# 抽象漏洞法则

> 原文：[The Law of Leaky Abstractions](https://www.joelonsoftware.com/2002/11/11/the-law-of-leaky-abstractions/) · 作者：Joel Spolsky（2002年11月11日） · [查看英文原版](./en.md)

![抽象漏洞法则](/images/leaky-abstractions/leaky-abstractions.webp)

在互联网工程体系里，有一项你每天都在依赖的核心魔法。它就发生在 TCP 协议之中，这也是整个互联网最核心的基石之一。

TCP 是一种**可靠的（reliable）**数据传输方式。我说的“可靠”意思是：只要你通过网络用 TCP 发送一条消息，它就一定会送达，而且绝不会变成乱码或发生损坏。

我们在很多日常场景里都在用 TCP，比如打开网页、收发电子邮件。正因为 TCP 的可靠性，每一封电子邮件送到你手里时才能一字不差、完好无损。哪怕它只是一封蠢透了的垃圾邮件。

相比之下，还有另一种叫作 IP 的数据传输方式，它是**不可靠的（unreliable）**。没有任何人向你保证数据一定能送到，而且数据在半路上随时可能被搞得面目全非。如果你用 IP 协议一口气发出一堆消息，最后只有一半能到，你完全不必大惊小怪；而在送达的这一半里，有些消息的先后顺序跟发出时完全颠倒了，还有些消息干脆被替换成了别的内容，里头兴许塞着几张呆萌小猩猩的照片，但更大概率是一堆根本没法看的乱码，就像你邮箱里偶尔收到的外文垃圾邮件一样。

真正的魔法来了：==TCP 是直接架设在 IP 之上的。换句话说，TCP 必须想方设法，**只靠一个不可靠的工具，去完成可靠的数据传输**。==

为了让你直观感受到这件事为什么堪称魔法，不妨设想下面这个在逻辑上完全等价、虽然听起来有点荒诞的现实场景。

假设我们现在要把一批百老汇演员从纽约运送到洛杉矶好莱坞，唯一的办法是把他们塞进汽车，横穿整个美国开过去。路上有些车出了车祸，可怜的演员当场丧命；有些演员在半路喝得酩酊大醉，要么把自己剃成了光头，要么在鼻子上纹了个身，结果变得太丑，根本没法在好莱坞出镜；而且因为每辆车走的路线各不相同，演员们抵达好莱坞的先后顺序经常跟出发时完全不一样。现在，假设市面上推出了一项名叫“好莱坞特快（Hollywood Express）”的全新服务，专门负责把演员运送到好莱坞，并且向客户做出三大铁律承诺：（a）必定送达；（b）严格按出发顺序抵达；（c）演员状态完好无损。神奇的地方在于，“好莱坞特快”手头并没有任何黑科技交通工具，它唯一能用的办法，依然是把演员塞进汽车、横穿全国开过去那套极不可靠的老路子。那它是怎么运转的呢？每当一名演员抵达终点，“好莱坞特快”就会仔细检查他是否完好无损；如果缺胳膊少腿或者纹了鼻花，工作人员就会立刻给纽约总部打电话，要求把这名演员的同卵双胞胎兄弟派过来顶替。如果演员抵达的先后顺序乱了，“好莱坞特快”就在出口处把他们重新排好队。假如有一架飞往 51 区的大型不明飞行物（UFO）在内华达州的高速公路上坠毁，导致道路彻底瘫痪，所有原定走这条路的演员都会被自动改道，绕行亚利桑那州开过去，而“好莱坞特快”甚至根本不会向加州的电影导演们透露半个字。在导演们看来，无非是这批演员比平时稍微晚到了一小会儿，他们甚至压根不会*听说*有 UFO 坠毁这档子事。

这，大体上就是 TCP 的魔法。计算机科学家喜欢把这种东西称为**抽象（Abstraction）**：把底层正在发生的极其复杂的机制加以简化，在表面呈现出一个干净简单的接口。事实证明，计算机编程的很大一部分工作，本质上就是在构建各种各样的抽象。什么是字符串库？它是一种让你假装计算机处理文本字符串能像处理数字一样轻松自如的把戏。什么是文件系统？它是一种让你假装硬盘根本不是一堆高速旋转、在特定物理位置记录磁比特的磁性盘片，而是一套文件夹套着文件夹、里面装着一个个由字节串组成的文件的层级系统。

回到 TCP 的话题。刚才为了方便解释，我其实撒了一个善意的小谎，估计这会儿有些懂行的读者已经听得七窍生烟、恨不得跳起来纠正我了。我刚才说 TCP 能“保证”你的消息一定送达。其实它保证不了。如果你养的宠物蛇把连着你电脑的网线给咬断了，导致*没有任何一个* IP 数据包能传过去，那 TCP 也回天乏术，你的消息根本不可能送达。又或者，如果你平时对公司的系统管理员说话没大没小，他们为了给你点颜色看看，故意把你的网线插进了一台严重过载的集线器（Hub）里，导致你的 IP 数据包只有一小部分能挤过去；这时候 TCP 确实还能正常干活，但你的所有网络操作都会变得慢如蜗牛。

这就是我所说的**抽象漏洞（Leaky Abstraction，常译作“抽象泄漏”）**。TCP 试图在底层不可靠的网络之上提供一个完美无瑕的完整抽象，但有些时候，底层的网络依然会顺着抽象的裂缝渗透出来，让你真切地感受到那些抽象层根本护不住你的底层风浪。而这，仅仅是我称之为“抽象漏洞法则（The Law of Leaky Abstractions）”的一个缩影：

> ==**所有非平凡的抽象，在某种程度上都是有漏洞的。**==
> （All non-trivial abstractions, to some degree, are leaky.）

抽象总会失灵。有时候漏得少一点，有时候漏得一塌糊涂。只要存在抽象，漏洞就无处不在，意外就随时会发生。下面我随便举几个例子：

- **二维数组遍历与虚拟内存：** 哪怕是像遍历一个大型二维数组这样再简单不过的操作，按行（水平方向）遍历和按列（垂直方向）遍历的性能也可能有着天壤之别，这完全取决于内存布局的“木纹走向（grain of the wood）”。其中一个方向引发的**缺页中断（page faults）**可能会比另一个方向多出成千上万倍，而磁盘缺页中断是极其缓慢的。按理说，哪怕是写汇编语言的程序员，系统也允许他们假装自己拥有一整块平坦连续的巨大内存地址空间；但虚拟内存机制意味着这其实只是一层抽象。一旦发生缺页中断，这层抽象就会漏水，某些内存读取操作耗费的纳秒数就会比其他内存读取高出好几个数量级。
- **SQL 查询与执行计划：** SQL 语言的设计初衷，是把查询数据库所需的具体过程化步骤（procedural steps）抽象掉，让你只需要声明“你想要什么数据”，然后由数据库引擎自己去琢磨“怎么把数据查出来”的具体步骤。但在某些情况下，两条在逻辑上完全等价的 SQL 查询语句，执行速度却可能相差几千倍。一个非常有名的例子是：在不少 SQL 数据库服务器上，如果你在查询条件里写上 `where a=b and b=c and a=c`，执行速度会比只写 `where a=b and b=c` 快上无数倍，哪怕两者的查询结果集分毫不差。按理说，作为使用者，你根本不应该去操心底层的执行过程，只需要关心逻辑声明就够了。但有些时候，这层抽象偏偏就会漏水，酿成灾难性的性能雪崩；到那时候，你不得不掏出查询计划分析器（Query Plan Analyzer），一行行去研究数据库引擎到底哪根筋搭错了，然后绞尽脑汁想办法让你的查询跑得快一点。
- **NFS / SMB 网络文件系统：** 尽管像 NFS 和 SMB 这样的网络文件系统库，允许你把远程机器上的文件当作“就跟在本地硬盘上一样”去读写，但网络连接有时会变得极其缓慢甚至直接断开，这时候远程文件就再也没法装作跟本地文件一样了，而作为程序员，你必须专门写代码去处理这种异常。==“远程文件等同于本地文件”这层抽象[漏水了](https://www.joelonsoftware.com/articles/fog0000000041.html)。== 这里给 Unix 系统管理员举一个非常具体的例子：假如你把用户的家目录（home directories）放在通过 NFS 挂载的远程磁盘上（这是第一层抽象），而你的用户在自己的家目录下创建了 `.forward` 文件，用来把收到的所有电子邮件自动转发到其他邮箱（这是第二层抽象）。如果在新邮件到达的那一刻，NFS 服务器恰好宕机了，那么这些邮件就根本不会被转发，因为邮件系统找不到那个 `.forward` 文件。抽象层里的这道裂缝，实实在在地导致几封邮件在半路上凭空蒸发了。
- **C++ 的字符串类（`string`）：** C++ 的各种 `string` 类库原本是为了让你假装字符串是语言里的“一等公民”数据类型。它们试图把“[字符串在底层其实很难搞](https://www.joelonsoftware.com/articles/fog0000000319.html)”这一残酷事实抽象掉，让你像操作整数一样轻松地操作字符串。几乎所有的 C++ `string` 类都重载了 `+` 运算符，这样你就可以直接写 **`s + "bar"`** 来拼接字符串。但你知道最要命的是什么吗？无论类库作者多么呕心沥血，地球上没有任何一个 C++ `string` 类能让你直接写出 **`"foo" + "bar"`** 这样的代码，因为在 C++ 语言里，双引号括起来的字符串字面量永远是 `char*`（字符指针），绝不是真正的 `string` 对象（两个指针相加在 C/C++ 中是非法或无意义的）。这层抽象裂开了一个大口子，而且受限于语言本身的机制，你根本没法把这个口子堵上。（说来好笑，C++ 语言这些年来的演进史，很大程度上简直就是一部试图修补字符串抽象漏洞的血泪史。至于他们当年为什么不干脆在语言核心里直接内置一个原生的 `string` 类型，我到现在也想不明白。）
- **雨天开车与打滑：** 下雨天开车的时候，你就是没法像晴天开得那么快。哪怕你的汽车装了雨刮器、大灯、车顶和暖风空调，所有这些配置都在试图保护你，让你不必在意“外面正在下雨”这个事实（也就是说，它们把天气给抽象掉了）；但看呐，你依然得提心吊胆地防着**水滑效应（hydroplaning，英国人叫 aquaplaning，即轮胎与路面之间形成水膜导致失控打滑）**，而且有时候暴雨实在太大，你根本看不清前方多远的路况，所以一到下雨天你还是得乖乖减速慢行。因为受制于抽象漏洞法则，天气永远不可能被彻底抽象掉。

抽象漏洞法则之所以让人头疼，其中一个重要原因在于：它意味着抽象并没有像它们承诺的那样，真正把我们的开发生活简化到哪里去。当我在培训一名 C++ 新手程序员时，如果我永远不需要教他们什么是 `char*`、什么是指针运算，直接带他们用标准模板库（STL）里的 `string`，那该有多美好啊！但总有一天，他们会顺手写出 **`"foo" + "bar"`** 这样的代码，然后程序会发生极其诡异的报错或崩溃；到那个时候，我还是得停下来，把关于 `char*` 指针的底层机制从头到尾给他们讲个遍。又或者某一天，他们试着去调用一个 Windows API 函数，文档上赫然写着该函数需要传入一个 `OUT LPTSTR` 类型的参数；如果他们不去把 `char*`、指针、Unicode 编码、`wchar_t` 宽字符以及 `TCHAR` 头文件那套历史包袱全部搞懂，他们根本不可能明白这个函数到底该怎么调用。所有这些被藏在底层的脏活累活，最终全都顺着裂缝往上冒了出来。

在教别人做 COM 编程的时候，如果我只需要教他们怎么点点鼠标用 Visual Studio 的向导（Wizards）和各种自动生成代码的功能，那该有多省事。可一旦程序出了任何一点差错，他们就会两眼一抹黑，完全不知道底下发生了什么，更不知道该怎么调试、怎么从故障中恢复。为了让他们能排查问题，我到头来还是得把 `IUnknown` 接口、`CLSID`、`ProgID` 等一整套繁琐的底层机制原原本本地教给他们……老天爷啊，真是造孽！

在教别人做 ASP.NET 编程的时候，如果我只需要告诉他们：“你在界面控件上双击一下，然后写一段在用户点击时在服务器端运行的代码就行了”，那该有多轻松。的确，ASP.NET 把“编写处理点击超链接（**`<a>`**）的 HTML 代码”与“编写处理点击按钮的 HTML 代码”之间的底层差异给抽象掉了。但问题在于：ASP.NET 的设计者们必须掩盖一个底层事实，那就是在标准 HTML 里，超链接本身是根本没法直接提交表单（Submit a form）的。为了做到这一点，他们在背后悄悄生成了几行 JavaScript 代码，并给那个超链接挂载了一个 `onclick` 事件处理器。然而，这层抽象同样会漏水。如果终端用户在浏览器里禁用了 JavaScript，这个 ASP.NET 应用程序就会彻底罢工；而如果写代码的程序员压根不知道 ASP.NET 在底层帮他抽象掉了什么东西，面对故障时他甚至连问题出在哪儿都摸不着头脑。

==抽象漏洞法则意味着：每当有人发明了一款酷炫夺目的新型代码生成工具，号称能让我们所有人的开发效率突飞猛进时，你总会听到很多老手在旁边苦口婆心地劝告：“先学会怎么纯手工把它写出来，然后再用那个酷炫的工具去省时间。”== 那些试图把底层细节抽象掉的代码生成工具，就像世上所有的抽象一样，迟早都会漏水；而想要在漏水时游刃有余地收拾残局，唯一的办法就是去彻底弄懂这些抽象在底层究竟是怎么运作的，以及它们到底掩盖了什么。**因此，抽象确实节省了我们干活的时间，却省不了我们学习的时间。**

而这一切导向了一个极具讽刺意味的悖论：尽管我们手头的编程工具层级越来越高，抽象封装做得越来越好，但**想要成为一名真正精通业务的优秀程序员，门槛反而变得越来越高了**。

当年我在微软做第一份实习生工作时，我的任务是为苹果 Macintosh 电脑编写字符串处理库。当时一个非常典型的开发任务是：写一个定制版的 **`strcat`** 函数，让它在拼接完字符串后返回指向新字符串末尾的指针。总共也就几行 C 语言代码。我干的所有活儿，知识点全都出自 K&R 那本薄薄的《C 程序设计语言》小册子（即 Brian Kernighan 与 Dennis Ritchie 合著的 C 语言圣经）。

而到了今天，为了开发我们公司的桌面内容管理系统 CityDesk，我必须同时精通 Visual Basic、COM、ATL、C++、InnoSetup 安装包脚本、Internet Explorer 浏览器内核机制、正则表达式、DOM、HTML、CSS 以及 XML。跟当年 K&R 书里那套原始的 C 语言比起来，这些全都是高大上的高层抽象工具；但最要命的是，我不仅得学会这一大堆高层工具，当年 K&R 书里那些底层原理我依然得烂熟于心，否则一旦遇上底层故障，我分分钟就会死得很难看。

十年前，我们或许曾天真地以为，层出不穷的新型编程范式到了今天应该已经让写代码这件事变得轻而易举了。平心而论，我们这些年来创造出的无数抽象，*确实*让我们有能力去驾驭十年前或十五年前根本不敢想象的全新软件复杂度量级，比如图形界面（GUI）编程和网络编程。像现代面向对象（OO）的可视化窗体语言这类优秀工具，确实能让我们以快得惊人的速度把一大堆日常功能堆出来；但冷不丁某一天，只要遇上一个“抽象层漏水”引发的诡异 Bug，光排查这一个问题就能足足卡上你两个星期。这也解释了为什么当你想招一名平时主要写 VB 代码的程序员时，只招一个“仅仅会写 VB 的程序员”是远远不够的；因为每当 VB 的抽象层发生泄漏，这种只懂表层工具的程序员就会像掉进沥青坑里一样，彻底陷死在里面动弹不得。

抽象漏洞法则，正在拽着我们所有人往下沉。
